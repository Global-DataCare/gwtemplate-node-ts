Guía reproducible para el alta y despliegue de un host

Documento público en español para memoria, consultoría e integración.

1. Qué es el recolector de evidencias

El término «runner SEDIA» es informal. No es Helm ni una herramienta oficial de SEDIA. Es el recolector público scripts/collect-open-source-production-readiness-evidence.sh, invocado mediante npm run evidence:open-source-production-readiness. Ejecuta las pruebas y genera estados, logs saneados, resumen y manifiesto con hashes.

2. Flujo objetivo

Autorización del host
        ↓
HostingServiceCredential (VC JSON y VC-JWT)
        ↓
Registro gobernado en la ICA de Fabric
        ↓
Enrolamiento MSP y TLS con claves privadas locales
        ↓
Secrets de Kubernetes
        ↓
helm upgrade --install gdc-host
        ↓
Peer + CouchDB + GW CORE + PostgreSQL + IPFS + CCAAS
        ↓
Canales, escritura, lectura, denegación y reinicio

3. Evidencia ejecutada

  • CA del espacio de datos local con Root e Issuer desechables.
  • ICA del espacio de datos y Host VC JSON/VC-JWT sin PDF para un host preautorizado.
  • ICA de Fabric, certificados MSP/TLS, Host1MSP, Host2MSP, canales y chaincodes.
  • GW CORE, PostgreSQL e IPFS con escritura, lectura y recuperación tras reinicio.
  • Instalación real mediante kind y Helm de un peer del Host2MSP recién admitido, CouchDB, GW CORE, PostgreSQL, IPFS y nueve runtimes CCAAS.
  • Unión del peer Kubernetes a los canales locales, instalación y aprobación de los paquetes CCAAS exactos.
  • La misma Host VC queda vinculada a los certificados del peer y del cliente GW; GW firma como Host2MSP y se dirige al peer Kubernetes de ese MSP, con persistencia y nueva capacidad de endoso tras reiniciar GW, peer y CCAAS.
  • Acceso consentido y controles negativos de acceso no autorizado.
Separación comprobada: Docker mantiene la ICA de Fabric, el orderer y un peer de referencia como red externa. El peer desplegado por Helm se une a esa red y el GW endosa exclusivamente mediante ese peer Kubernetes; la ruta al peer Docker solo se usa para gossip/bootstrap.

4. Qué hace realmente la puerta Kubernetes

La prueba ya no se limita a helm template. Crea un clúster kind aislado, namespace y Secrets; carga la imagen aprobada; ejecuta helm upgrade --install; espera el rollout; realiza operaciones E2E; comprueba canales y CouchDB; consulta PostgreSQL e IPFS dentro de los pods; instala y aprueba los nueve paquetes CCAAS en el peer Kubernetes; ejecuta Consent y SMART mediante ese peer; reinicia GW, peer y CCAAS y comprueba la recuperación. helm template permanece como comprobación estática complementaria.

5. Promoción del mismo chart

EntornoChartDiferencias
local-networkgdc-hostImágenes y autoridades locales, DNS .localhost y StorageClass de kind.
test-networkgdc-hostDigests publicados, autoridades de staging, DNS/TLS y almacenamiento cloud.
Produccióngdc-hostHost VC y certificados nuevos, digests aprobados, KMS y values del proveedor.

No se reutilizan MSP, TLS, claves, Secrets, grants ni credenciales verificables entre entornos. Se reutilizan el chart, su estructura de configuración y las versiones o digests aprobados.

6. Responsabilidad de Helm

Helm no crea la red Fabric, no actúa como administrador de ninguna ICA y no decide qué MSP entra en los canales. Antes de instalar un host autónomo deben existir la autorización, el grant de enrolamiento, el material MSP/TLS generado por el host, la incorporación gobernada a los canales y los Secrets Kubernetes. La reconciliación privilegiada se ejecuta por la autoridad.

La autorización exige una HostingServiceCredential también en local-network y test-network. «Sin PDF» significa que la ICA del espacio de datos puede emitir esa VC para un host preautorizado; no significa omitir la credencial. La ICA de Fabric registra después un identificador limitado a dos enrolamientos, uno MSP y otro TLS, y otro identificador de un solo uso para la identidad cliente del GW. Las tres claves privadas se generan dentro del host. El helper aplica issuedAt/expiresAt; la autoridad debe revocar el identificador no consumido porque Fabric CA garantiza el límite de usos, no esa fecha.

7. Datos requeridos al proveedor

  • Versión de Kubernetes, namespace, StorageClass e IngressClass.
  • DNS, TLS, reglas de red y registro de imágenes.
  • PVC, backups, restauración y observabilidad.
  • Gestor de secretos y custodia externa del KEK.
  • Valores no secretos del release y canal seguro para grants y Secrets.

8. Criterio de presentación

La memoria puede afirmar que la red Fabric local y el despliegue Kubernetes con peer, CouchDB, GW CORE, PostgreSQL, IPFS y CCAAS se han probado de forma reproducible, incluido el lifecycle CCAAS y el E2E del GW contra el peer Kubernetes. La promoción a otra red conserva el chart, pero exige nuevas credenciales, Secrets, digests, values y reconciliación gobernada.

9. Prueba completa del auditor

export REPO_ROOT="$(pwd)"
export DATASPACE_CA_ROOT="/ruta/al/checkout/dataspace-ca-ts"
export DATASPACE_ICA_ROOT="/ruta/al/checkout/dataspace-ica-ts"
cd "${REPO_ROOT}"
npm ci
release_tag="$(node -p "require('./package.json').version")-$(git rev-parse --short HEAD)"
export IMAGE_NAME="gw-core:${release_tag}"
LOCAL_IMAGE_NAME="${IMAGE_NAME}" ./docker_build_local.sh
npm run evidence:open-source-production-readiness

El auditor conserva el directorio anunciado bajo artifacts/open-source-production-readiness/, comprueba todos los estados PASS y verifica los hashes. Ningún grant, token, PDF, clave, IP o fichero env forma parte de la evidencia pública.

10. Fases de autorización y enrolamiento

La autoridad recibe por canal seguro la petición con URL, MSP, Host VC-JWT, decisión firmada, DID públicos, JWKS e inventario gobernado. Ejecuta:

request_id="$(jq -r '.governanceDecision.decision.requestId' \
  /secure/approvals/host-enrollment-request.json)"
node scripts/onboarding/host-onboarding-assistant.mjs \
  --manifest /secure/onboarding/onboarding.json --role authority
node scripts/onboarding/host-onboarding-assistant.mjs \
  --manifest /secure/onboarding/onboarding.json --role authority \
  --apply --confirm-request "${request_id}"

El proveedor recibe únicamente el grant 0600 y la cadena TLS pública de Fabric CA. Las claves se crean en su infraestructura:

node scripts/onboarding/host-onboarding-assistant.mjs \
  --manifest /secure/onboarding/onboarding.json --role host
node scripts/onboarding/host-onboarding-assistant.mjs \
  --manifest /secure/onboarding/onboarding.json --role host \
  --apply --confirm-request "${request_id}"
cd /secure/host/helm-runtime
shasum -a 256 -c manifest.sha256

El paquete resultante contiene solo msp.tgz, tls.tgz, authorization.json y manifest.sha256.

11. Imagen OCI, values y package IDs

docker build -t "${OCI_REPOSITORY}/gw-core:${release_tag}" .
docker push "${OCI_REPOSITORY}/gw-core:${release_tag}"
docker buildx imagetools inspect "${OCI_REPOSITORY}/gw-core:${release_tag}"

GW CORE es un servicio y no se publica en npm. El values usa el digest OCI. Cada CCAAS necesita una imagen por digest y un paquete cuya dirección sea el Service exacto del release. El package ID es <label>:<sha256 del .tgz>; cualquier cambio de Service, release, puerto o TLS obliga a regenerarlo.

HOST_FULLNAME="${HELM_RELEASE}" \
KUBE_NAMESPACE="${KUBE_NAMESPACE}" \
CCAAS_IMAGE="${OCI_REPOSITORY}/host-runtime@sha256:<digest>" \
CCAAS_OUTPUT_DIR=/secure/onboarding/ccaas \
  bash scripts/onboarding/prepare-ccaas-packages.sh
shasum -a 256 -c /secure/onboarding/ccaas/manifest.sha256

El resultado contiene nueve archivos, sus package IDs en manifest.tsv y el fragmento chaincodes.values.yaml.

12. Secrets e instalación Kubernetes

export KUBE_CONTEXT="contexto-del-cluster"
export KUBE_NAMESPACE="namespace-del-host"
export HELM_RELEASE="nombre-del-host"
kubectl --context "${KUBE_CONTEXT}" create namespace "${KUBE_NAMESPACE}"
HOST_RUNTIME_DIR=/secure/host/helm-runtime \
POSTGRES_SECRET_ENV_FILE=/secure/host/postgresql.env \
COUCHDB_SECRET_ENV_FILE=/secure/host/couchdb.env \
GW_SECRET_ENV_FILE=/secure/host/gw.env \
REDIS_SECRET_ENV_FILE=/secure/host/redis.env \
  bash scripts/onboarding/materialize-kubernetes-secrets.sh
bash scripts/validate-host-helm-values.sh \
  /secure/inventory/host.values.yaml "${KUBE_NAMESPACE}" "${HELM_RELEASE}"
helm upgrade --install "${HELM_RELEASE}" charts/gdc-host \
  --kube-context "${KUBE_CONTEXT}" --namespace "${KUBE_NAMESPACE}" \
  --values /secure/inventory/host.values.yaml \
  --atomic --wait --timeout 15m

Se materializan seis Secrets básicos —peer MSP, peer TLS, autorización, PostgreSQL, CouchDB y GW— y un séptimo si Redis está habilitado. Los values nunca contienen sus valores. En producción cada pod desenvuelve una vez la KEK mediante el adaptador KMS; una KEK plana solo es válida en local/demo.

13. Reconciliación y aceptación

node scripts/onboarding/host-onboarding-assistant.mjs \
  --manifest /secure/onboarding/onboarding.json --role platform
node scripts/onboarding/host-onboarding-assistant.mjs \
  --manifest /secure/onboarding/onboarding.json --role platform \
  --apply --confirm-request "${request_id}"
kubectl --context "${KUBE_CONTEXT}" -n "${KUBE_NAMESPACE}" get pods,pvc,svc
kubectl --context "${KUBE_CONTEXT}" -n "${KUBE_NAMESPACE}" rollout status \
  statefulset/"${HELM_RELEASE}"-peer --timeout=5m
kubectl --context "${KUBE_CONTEXT}" -n "${KUBE_NAMESPACE}" rollout status \
  deployment/"${HELM_RELEASE}"-gw --timeout=5m

El mapa privado del operador contiene comandos reales de inspección y aplicación para MSP, grants, peer, canales y lifecycle CCAAS. Si falta uno, el reconciliador falla cerrado. La aceptación prueba escritura/lectura por el peer propio, permiso/denegación y persistencia tras reiniciar GW, peer y CCAAS; un pod arrancado no basta.

14. Material que se entrega

Commit, digest OCI, chart, values saneado, versiones, gates, logs saneados, auditoría y manifiesto de hashes. Los datos reales del proveedor se mantienen en un anexo privado. La prueba local demuestra reproducibilidad del software; no declara desplegada una infraestructura externa concreta.

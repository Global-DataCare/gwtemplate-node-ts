# Open-Source Production Readiness

This repository generates a reproducible public evidence package with:

```bash
IMAGE_NAME="gw-core:<version>-<commit>" \
  npm run evidence:open-source-production-readiness
```

The command writes public execution evidence to
`artifacts/open-source-production-readiness/<UTC>/`. The directory is ignored
by Git because it contains generated execution results rather than source code.
A project report can attach `SUMMARY.md`, `manifest.json`, `logs/`, and the
synthetic public CA publication generated by the run.

## Evidence gates

| Gate | Service or role | Evidence |
| --- | --- | --- |
| 10-11 | Offline dataspace CA | Tests, disposable Root/issuer material, DID/JWKS/trust publication, and verified X.509 chain |
| 20 | Online dataspace ICA | Host-form extraction and signed `HostingServiceCredential` issuance |
| 30 | Fabric governance | Credential verification, signed decision, operator grant, idempotent plan, and audit record |
| 31 | Local Fabric network | `Host1MSP` and `Host2MSP` joined to `identity-local` and `health-care-local` |
| 35 | Human identity taxonomy | EU organization/employee on `identity-eu`; human individual on `identity-global` |
| 36 | Employee onboarding | Medical-secretary creation, professional identity issuance, and DCR |
| 40 | Host runtime | GW image, PostgreSQL, IPFS/Kubo, Fabric, consent, SMART access, and restart recovery |
| 60 | Public evidence hygiene | Redaction and secret scanning before the package is completed |

The offline dataspace CA, dataspace ICA, and Fabric ICA are separate
operational boundaries:

- the offline dataspace CA publishes the trust anchor and signs issuer requests;
- the dataspace ICA verifies signed legal evidence and issues participant VCs;
- the Fabric ICA enrolls MSP, peer, orderer, and client identities.

The local gate connects disposable material produced by `dataspace-ca-ts` to
the Docker Fabric CAs. Private CA keys are removed and never copied into the
evidence package. Fabric CA enrollment passwords are redacted while the run is
being logged, and the final gate fails if a known development secret remains.
Before GW starts, the runtime gate warms every identity chaincode so first-use
container startup is not mistaken for a missing endorsing peer.

## Hosts, MSPs, and tenants

The local topology contains two Fabric members:

```text
Fabric local-network
├── Host1MSP -> peer0-host1
└── Host2MSP -> peer0-host2
```

The corresponding peer DNS names, containers, Fabric CA affiliations and
cryptographic paths use `host1` and `host2`; the Fabric membership identities
are `Host1MSP` and `Host2MSP`.

A VAT-addressed tenant `Organization` is business data hosted by a GW. Hosting
an organization does not assign that tenant an MSP or peer. One operator may
run multiple peers under one MSP when the governance policy permits it.

## Sector and channel boundaries

`onehealth-research` is a GW sector/capability, not a Fabric channel.

| Environment | Identity | Data |
| --- | --- | --- |
| `local-network` | `identity-local` | `health-care-local` |
| EU test/production organization and employee | `identity-eu` | `health-care-eu` |
| Human individual in test/production | `identity-global` | `health-care-eu` when EU health data exists |

Test and production may reuse logical channel names, but remain independent
networks with separate blocks, MSPs, secrets, and data.

This evidence package covers human identities and services. It does not claim
animal identities, veterinary services, or `animal-*` channels as verified.

## Supported report claims

The evidence package proves:

1. reproducible offline trust-plane publication;
2. host activation and hosting-credential issuance;
3. a deterministic cryptographic governance-admission contract;
4. a real two-host-MSP Fabric topology;
5. portable PostgreSQL and IPFS persistence;
6. Fabric writes/reads and Consent/SMART flows;
7. host and tenant recovery after restarting the same image;
8. person health-data creation and authorized medical-secretary IPS access,
   with denial for another employee without consent.

The selected production profile keeps one VAT-backed tenant while temporarily
serving both entity/employee and individual routes from the same host. This
does not merge identity planes: the organization and employees use
`identity-eu`, while the natural person uses `identity-global`. Gate 36 proves
employee onboarding and DCR. Gate 40 proves live data creation, consent, SMART
token issuance, IPS read access, and the negative access-control case.

The package does not yet prove that `Host2MSP` was dynamically admitted to
channels that were already running with only `Host1MSP`. The reconciler and
its controls are tested, but the operator-owned mutation driver still needs a
live-network E2E. A production report must present this as a promotion gate,
not as an already verified capability.

## Production equivalence

Before deploying the same image by digest:

1. replace the local KEK with a process-owned KEK unwrapped once during
   bootstrap through the configured KMS adapter;
2. use production secrets, DNS, TLS, persistent volumes, backups, and
   monitoring;
3. use the governed production Fabric Root/ICA and channel inventory;
4. run the real dynamic second-host admission E2E;
5. verify `/host/ping`, OpenAPI, public DID/JWKS, effective channels and MSP,
   persistence, and recovery.

`KEK_SECRET`, the disposable CA, and deterministic devnet enrollment material
are local demonstration resources and do not represent production custody.

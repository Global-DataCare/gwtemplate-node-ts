# Organization registration authorization audit

## Runtime policy

Host `Organization/_transaction` has two explicit verification sources:

- no authorization VC: forward the legal evidence to ICA;
- attached `OrganizationRegistrationAuthorizationCredential`: accept only
  when `resource.verification.resourceType` is exactly `test-network`.

The Test Network verifier requires `HOST_ORGANIZATION_AUTHORIZATION_ISSUERS`
to contain the exact VC issuer DID. It resolves the issuer and signer did:web
documents at transaction time and checks that the signer is still in the
issuer's `controller` relation, that the proof key remains an assertion method,
and that neither signer document nor credential is expired/revoked. It then
verifies the detached ML-DSA-65 proof and exact organization DID/identifier,
controller email, RFC 9278 public-key commitment and delivered postal licence.

Failure of any check is a security error. The host never falls back from a bad
attached VC to ICA and never accepts the Test Network VC for another resource
type. The response records `verificationResponse` for this source; legacy ICA
responses retain `icaResponse`.

## Boundaries

This transaction creates the pending tenant registration and Offer. It does
not prove Order acceptance, redeem the postal code, complete DCR, activate the
tenant or change Fabric membership. The same postal code must be imported into
the authoritative licence lifecycle before `_exchange`; that portal-to-GW
integration remains a deployment gate until end-to-end evidence exists.

Production remains ICA-backed. Qualified-signature and certificate policy must
not be inferred from the Test Network ML-DSA proof.

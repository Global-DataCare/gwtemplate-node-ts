## 1. Scope

This document focuses on:
- Provider discovery for Family apps (operator-first).
- Family Organization onboarding (`individual/org.schema/Organization`).
- Relationship/member bootstrap after the family is created.

## 2. Step 1 (Mandatory): Discover Providers From Operator Catalog

Before creating a family in a provider, the app must resolve the provider list from known operator DIDs.

Runtime contract:
- Input: `FAMILY_OPERATOR_DIDS` configured in the app environment.
- Per operator DID:
  1. Resolve DID Document.
  2. Read `CatalogService.serviceEndpoint`.
  3. Call DSP catalog request endpoint.
  4. Parse canonical DSP `dcat:Catalog` (DCAT/ODRL JSON-LD).

Backend endpoints (project-local DSP binding used in this project):
- `POST /host/cds-{hostCoverageScope}/{version}/{hostNetwork}/dsp/catalog/request`
- `GET /host/cds-{hostCoverageScope}/{version}/{hostNetwork}/dsp/catalog/datasets/{id}`
- Hosted tenant form:
  - `POST /{tenantId}/cds-{jurisdiction}/{version}/{sector}/dsp/catalog/request`
  - `GET /{tenantId}/cds-{jurisdiction}/{version}/{sector}/dsp/catalog/datasets/{id}`

The DSP standard HTTPS binding path is `/catalog/request`. GW CORE currently
publishes the equivalent capability through the project-local `/dsp/...`
binding shown above.

Notes:
- Dataset `id` is a dataset identifier, not a hardcoded `"providers"` keyword.
- Filtering is submitted in request body as `filters` (project contract), for example:
  - `filters.sector`
  - `filters.jurisdiction`

## 3. Step 2: Create Family Organization In Selected Provider

Once a provider is selected from catalog discovery, create the family under that provider:
- `POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/individual/org.schema/Organization/_batch`

Then complete the Offer/Order handshake:
- `POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/individual/org.schema/Order/_batch`

## 3.0. Claim Model For `individual/org.schema/Organization`

For the current individual/family onboarding contract, do not model the legal
representative as a separate top-level `Person` resource.

Use one claimset with four semantic zones:

- `Organization.*`
  - the indexed subject itself
  - example: `Organization.alternateName`
- `Organization.owner.*`
  - the operational binding between the indexed subject and the legal
    representative/controller
  - use this block for contact and lookup fields such as:
    - `Organization.owner.email`
    - `Organization.owner.telephone`
    - `Organization.owner.identifier.value`
- `Person.*`
  - the identity attributes of that same legal representative/controller
  - typical source: KYC, signer certificate, or typed form fields
  - examples:
    - `Person.givenName`
    - `Person.familyName`
    - `Person.name`
    - `Person.identifier.value`
    - `Person.birthDate`
    - `Person.gender`
- `Order.*`
  - the contractual acceptance of the index service
  - examples:
    - `Order.orderDate`
    - `Order.orderedItem.url`
    - `Order.orderedItem.category`
    - `Order.orderedItem.serviceType`

Operational rule:

- `Person.*` carries identity.
- `Organization.owner.*` carries contact plus the binding to that identity.
- `Organization.owner.identifier.value` should match the canonical controller
  identifier used in `Person.identifier.value` whenever both are present.

## 3.1. Swagger `/api-docs` Testing Notes

Family flows use the same Swagger helper described in `docs/90.A-API_INTEGRATORS_GUIDE.md` (`Global Flow Context`).

Recommended for repeated tests:
- Set `tenantId`, `sector`, and `jurisdiction` in the panel before executing Family endpoints.
- Use a unique `test id` per run so all `jti/thid` templates become unique (`...-<test-id>`).
- Keep `tenantId` aligned with canonical `Organization.identifier.value`. For legal organizations, use the same value for `tax id`.
- In Family onboarding, `alternateName` is part of the current subject/family bootstrap input.
  It is not the recommended first teaching claim for legal organization activation.

## 4. Why This Is First

The unified data index of the person is managed in the Family domain (role `ONESELF` and related controllers).
Therefore, provider selection via operator catalog is the first action before creating the family organization.

## 5. Swagger Organization

Swagger should expose Family-focused endpoints separately from Organization onboarding.
Recommended tags:
- `Family Discovery`
- `Family Onboarding`
- `Organization Onboarding`

In this codebase, catalog discovery endpoints are documented under the Family/Discovery tags, while common security and async contracts remain shared in the main guide.

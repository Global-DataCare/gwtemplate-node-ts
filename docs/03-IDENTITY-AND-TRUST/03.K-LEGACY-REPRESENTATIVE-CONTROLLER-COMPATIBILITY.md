# Legacy legal-representative controller compatibility

## Contract

The historical two-credential onboarding remains a first-controller bootstrap,
not an existing-tenant `_issue` exception:

- legacy `_verify` followed by `Organization/_activate` creates the tenant and
  keeps the verified legal representative as its first controller;
- the JWK submitted by that legacy portal belongs only to the legal
  representative performing the registration;
- when the signed PDF designates a different technical controller, that actor
  remains pending without a JWK or `ServiceControllerCredential` until it
  completes its own sector `_issue`, key binding and DCR;
- `Organization/_transaction` creates the pending registration and the
  following `Order/_batch` finalizes it with the same first-controller link;
- the controller employee DID produced during bootstrap is referenced by the
  organization DID from its first active version;
- submitting the same key again through `_activate` or `_transaction`
  upserts the controller idempotently when the tenant already exists, recreates
  its missing tenant collection if necessary and creates no new Offer;
- submitting a new verified portal key through the same authorized re-registration
  replaces only the legacy controller's DID key material; it does not remove or
  modify any other controller DID in the organization;
- a later controller enrollment channel `_issue` independently adds the service controller from
  its ICA-issued `ServiceControllerCredential` and never replaces the first
  controller.

An older re-verification that omits the technical-controller field does not
erase a prior signed designation and does not copy the representative JWK to
that actor. ICA retains only the normalized designation hash; no clear contact
value belongs in GW policy, logs or public DID output.

`Organization/_issue` does not reinterpret, restore or repair a
`LegalRepresentativeCredential`.

## Legacy deployment compatibility

Historical representative credentials may predate `RESPRSN` and embedded
`hasCredential` material. Enable the following switch only on a deployment
whose legacy portal still registers every organization through its verified
legal representative:

```text
HOST_LEGACY_REPRESENTATIVE_CONTROLLER=true
```

The switch never pins a tenant, sector, credential id, issuer or `kid`:
credential renewal, new organizations and representative portal-key rotation
must remain possible. Normal VP, credential, trust-registry and
service-authorization checks still authenticate every submission, and
`memberOf.taxID` must match the organization credential tax id. Compatibility
only suppresses the two obsolete legacy requirements (`RESPRSN` and embedded
representative key material).

## Persistence result

Both legacy creation paths build the representative controller employee before
finalizing the tenant and pass that controller DID into the organization DID.
The later service-controller `_issue` appends its DID using the canonical
`ServiceControllerCredential` checks. Each controller then uses its own
activation code, `Token/_exchange` and `Device/_dcr` lifecycle.

An accepted Order retry resolves its Offer from the searchable encrypted host
record, then compares the exact identifier only after KMS has unprotected the
authoritative registration claims. Repository projection metadata is not a
substitute for those protected claims. A matching active registration returns
the existing continuation material instead of requiring `pending` again.

This does not grant global controller authority to every representative VC.
It preserves, idempotently re-registers or rotates the historical first
controller only on a deployment that explicitly enables the legacy contract.
Ordinary employee lifecycle operations and later controller additions do not
consult this compatibility switch.

Tenant cryptographic provisioning is independently idempotent. An activation
or Order replay after a process restart must rehydrate the existing signing,
encryption, storage and HMAC material; it is never an implicit rotation event.
At startup the gateway compares each persisted tenant DID projection with the
recoverable KMS public keys. A mismatch is repaired by republishing those
public keys and re-signing an obsolete self-description while preserving the
DID identifier, aliases, controllers, services and organization claims. The
repair does not generate new keys and is not gated by the legacy representative
feature switch.

## Employee licences and device channels

New professional organizations start with at least two non-free assignments:
the verified representative seat and a contact-free technical-controller
reservation. The controller later binds that exact reservation through
`Organization/_issue`; promotional seats above two remain available.

This is never retroactive reassignment. If a historical organization already
uses its first seat for the representative and its second for a professional,
the gateway preserves both, creates no implicit third seat and requires a newly
added or purchased licence before another controller can bind. Startup may add
only a missing mandatory representative seat from protected verified tenant
claims; it never evicts another actor.

Employee creation and `License/_issue` remain separate operations so the
explicit issue response owns the activation credential.

Employee documents live in the resolved physical tenant collection; licence
documents remain in the logical tenant vault. A seat permits five active
device/channel bindings by default. Revoking one confirmed binding does not
release the employee seat. Only purging an already suspended employee releases
that licence.

An active controller may add explicit zero-price professional seats with
`License/_add` only in non-production `NETWORK_MODE=test` (in-memory),
`local-network`, or `test-network`. The operation creates available seats only.
`prod` or `network` rejects this shortcut and retains signed payment
confirmation plus ledger-verifiable Order processing.

## Deployment boundary

GW Core owns the reusable lifecycle behavior and keeps compatibility disabled
by default. Each deployment that still serves a legacy representative-first
portal enables it explicitly. The GKE wrapper propagates the value to the live
Deployment after applying shared manifests; a local profile alone is not
evidence that the policy is active.

## Operational verification

Use the read-only endpoint
`/{tenantId}/cds-{jurisdiction}/{version}/{sector}/.well-known/tenant-status.json`
to distinguish a missing controller (`required`), an issued controller
credential (`credential_issued`), completed DCR (`dcr_active`) and inconsistent
stored state. The projection contains controller DIDs and public key ids only.

DCR must update both the protected employee DID document and its blind `kid`
indexes. Historical records may contain the correct current keys with stale
bootstrap indexes. On an indexed miss, secure request verification may inspect
only the resolved tenant collection and logical vault, and it must match the
stored controller DID, signing `kid` and encryption `skid` together before
accepting the signature. The incoming envelope never supplies authority.

Before enabling employee creation, verify:

- the tenant route resolves instead of returning `404`;
- the organization DID references the historical controller DID before testing
  employee creation;
- each controller DID endpoint returns its own public verification methods;
- the historical controller DID publishes the key submitted by the verified
  legacy flow;
- after an independent controller enrollment flow, the organization DID references both
  intended controller DIDs and the modern credential material matches its JWK;
- each actor completes `_exchange` and DCR with its own activation code;
- no clear personal identifier was added to configuration, source, tests,
  documentation or logs.

# UNID legacy legal-representative controller compatibility

## Contract

The historical GlobalDataCare onboarding remains a first-controller bootstrap,
not an existing-tenant `_issue` exception:

- legacy `_verify` followed by `Organization/_activate` creates the tenant and
  keeps the verified legal representative as its first controller;
- `Organization/_transaction` creates the pending registration and the
  following `Order/_batch` finalizes it with the same first-controller link;
- the controller employee DID produced during bootstrap is referenced by the
  organization DID from its first active version;
- submitting the same key again through `_activate` or `_transaction`
  upserts the controller idempotently when the tenant already exists, recreates
  its missing tenant collection if necessary and creates no new Offer;
- submitting a new verified portal key through the same authorized re-registration
  replaces only the legacy controller's DID key material; it does not remove or
  modify any other controller DID in the organization;
- a later UNID portal `_issue` independently adds the service controller from
  its ICA-issued `ServiceControllerCredential` and never replaces the first
  controller.

`Organization/_issue` does not reinterpret, restore or repair a
`LegalRepresentativeCredential`.

## Legacy compatibility scope

Historical representative credentials may predate `RESPRSN` and embedded
`hasCredential` material. Configure
`HOST_LEGACY_CONTROLLER_SCOPES` only on the UNID GW deployment when that old
shape must remain accepted. It is a comma-separated list whose entries use
`<tenantId>|<sector>`. Every submission must match:

- tenant id;
- sector.

The scope never pins a credential id, issuer or `kid`: credential renewal and
portal-key rotation must remain possible. The normal VP, credential,
trust-registry and service-authorization checks still authenticate every
submission, and `memberOf.taxID` must match the organization credential tax id.
This compatibility scope only suppresses the two obsolete legacy requirements
(`RESPRSN` and embedded representative key material).

The scope must not contain a name, email address, portal username, credential
identifier, issuer DID or key identifier. Runtime claims may carry contact data
needed for delivery, but those values remain outside deployment policy.

UNID deployment value:

```text
HOST_LEGACY_CONTROLLER_SCOPES=VATES-G02793479|onehealth-research
```

## Persistence result

Both legacy creation paths build the representative controller employee before
finalizing the tenant and pass that controller DID into the organization DID.
The later service-controller `_issue` appends its DID using the canonical
`ServiceControllerCredential` checks. Each controller then uses its own
activation code, `Token/_exchange` and `Device/_dcr` lifecycle.

This does not make every legal representative a controller. It preserves,
idempotently re-registers or rotates the historical first controller through
the scoped legacy contract. Ordinary employee lifecycle operations and later
controller additions do not consult this compatibility scope.

## Product propagation boundary

This compatibility switch is specific to GW UNID. After the UNID changes are
merged to `main`, compare GW UNID and GW Core in both directions and propagate
only reusable controller lifecycle behavior; keep the UNID tenant scope out of
Core defaults. The future GW VetChain line is validated from GW UNID first,
before copying proven generic behavior back to the other gateway products.

## Operational verification

Before enabling employee creation, verify:

- the tenant route resolves instead of returning `404`;
- the organization DID references the historical controller DID before testing
  employee creation;
- each controller DID endpoint returns its own public verification methods;
- the historical controller DID publishes the key submitted by the verified
  GlobalDataCare flow;
- after the independent UNID portal flow, the organization DID references both
  intended controller DIDs and the modern credential material matches its JWK;
- each actor completes `_exchange` and DCR with its own activation code;
- no clear personal identifier was added to configuration, source, tests,
  documentation or logs.

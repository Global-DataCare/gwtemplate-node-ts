# Federated SMART token verification by a tenant Clearing House

## Purpose and status

This document defines the cross-custodian authorization contract in which an
individual index provider authorizes discovery and retrieval from resources
held by multiple independent EHRs, wearables and health-data services.

GW currently issues the index-provider SMART token and accepts a sibling
`body.vp_token`. The nested `client_assertion.vp` transition and the
custodian-tenant `_verify` endpoint defined below are not implemented. They
must not be advertised as current behavior until their route, manager, ledger,
integration and live E2E gates pass.

## Trust topology

The professional first obtains a scoped SMART token from the individual's
index provider. That token is presented to each EHR identified by the index.
The EHR holds the request pending, sends the original token to its own tenant
Clearing House, and accepts it only after receiving positive signed evidence
from the tenant it already trusts.

```text
professional application
  -> individual index provider: client_assertion plus professional VP
  <- individual index provider: index-audience SMART token
  -> custodian EHR: original SMART token and requested record
  -> EHR tenant: verify that foreign SMART token and its evidence
  <- EHR tenant: signed introspection response containing a compact JWT-VP
  <- custodian EHR: only records authorized by the original scope
```

The index provider remains the SMART token audience. Twenty independent EHRs,
portals or devices are not added as twenty OAuth audiences. Each EHR receives
the token as a federated authorization artifact and asks its own tenant whether
to accept it; it does not bypass that local trust decision.

## Stable vocabulary

These names are used consistently by GW, SDKs, BFF guides and EHR examples:

- `professionalCredential`: the original issuer-signed professional VC;
- `professionalPresentation`: the professional's VP containing that same VC;
- `indexSmartToken`: the scoped SMART token issued by the individual index
  provider with that provider as `aud`;
- `tenantVerificationResponse`: the signed introspection JWT returned by the
  custodian EHR's own tenant;
- `verifiedProfessionalPresentation`: the short-lived VP inside that response,
  containing the same original professional VC and bound to the original token.

There is no second professional VC and no renamed copy. The short-lived
artifacts are the tenant verification response and its presentation; the
professional credential inside them remains `professionalCredential`.

## SMART issuance and transitional VP placement

The client-authentication JWT retains the RFC 7523 and SMART
`private_key_jwt` claims: `iss` and `sub` identify the registered client,
`aud` identifies the index-provider SMART endpoint, and `jti` is short-lived
and single-use. The data-space profile additionally carries the holder's
transaction-bound presentation in `client_assertion.vp`.

During migration GW accepts either:

1. canonical `client_assertion.vp`; or
2. legacy sibling `body.vp_token`, with `body.presentation_submission` when
   required by the selected OpenID4VP profile.

When both are supplied, they must represent the same presentation and
professional subject. A mismatch is a security error; neither source silently
overrides the other. An issuer-signed professional VC retains its own proof
inside the VP. The outer assertion proves possession of the DCR client key and
does not replace the credential issuer's signature.

## Index-provider authorization checks

Before issuing the SMART token, the index provider requires all of these facts
to be current and mutually consistent:

- professional assignment is active and within its validity period;
- assignment belongs to the asserted legal organization;
- employee, assignment and device-key binding is active;
- signing key is active, unexpired, not revoked and allowed for signing;
- professional licence is active and permits the asserted role;
- active Consent, or governed break-glass policy, permits the exact subject,
  purpose, sections and operations requested.

The issued token preserves the verified presentation or a resolvable evidence
reference as well as its hash. A hash proves correlation but cannot by itself
let another tenant reconstruct and verify the professional credential.

## Custodian-tenant verification endpoint

The canonical data-space extension is:

```http
POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/identity/openid/smart/token/_verify
```

The EHR presents the original SMART token to its own tenant. The request is
authenticated with the EHR's registered `private_key_jwt` and uses an RFC
7662-compatible form body:

```http
Content-Type: application/x-www-form-urlencoded
Accept: application/token-introspection+jwt

token=<index-provider-smart-token>&
token_type_hint=access_token&
client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer&
client_assertion=<ehr-client-assertion>
```

This is profiled OAuth token introspection: the local tenant operates as the
EHR's trusted federated introspection proxy even though it did not issue the
foreign token and the EHR is deliberately not that token's `aud`. The tenant
must either validate the self-contained token under the configured
index-provider trust or obtain issuer-confirmed token state. It then resolves
the embedded or referenced professional VP and checks current assignment,
licence, binding and key state on the governed ledger. Missing or indeterminate
token or ledger evidence fails closed.

## Verification response

On success the tenant returns the signed JWT response defined by RFC 9701 with
JOSE `typ=token-introspection+jwt`, the tenant as top-level `iss`, the calling
EHR as top-level `aud`, and a `token_introspection` object. The profile adds
`token_introspection.vp_token`, using the OpenID4VP transport name for a compact
JWT-VP. After verifying and decoding that compact JWT, its payload claim `vp`
is `verifiedProfessionalPresentation` and contains the same original
professional VC that arrived inside `professionalPresentation`. The outer JWT
therefore remains an RFC 9701 introspection response, while the inner token
remains a standard JWT-VP. The EHR already trusts its tenant and therefore does
not need to query the ledger itself.

```json
{
  "iss": "<custodian-tenant-issuer>",
  "aud": "<registered-ehr-client>",
  "iat": 1788700000,
  "token_introspection": {
    "active": true,
    "iss": "<individual-index-provider>",
    "aud": "<individual-index-provider>",
    "sub": "<professional-did>",
    "scope": "<original-smart-scope>",
    "exp": 1788700300,
    "jti": "<original-smart-token-id>",
    "vp_token": "<compact-professional-jwt-vp>"
  }
}
```

The two nesting levels must not be collapsed or renamed:

```ts
const compactVp = introspectionPayload.token_introspection.vp_token;
const professionalPresentation = decodeJwt(compactVp).vp;
```

`vp_token` transports the presentation; `vp` is the JWT-VP payload claim. This
keeps the profile interoperable with OpenID4VP presentation handling without
claiming that RFC 7662 or RFC 9701 defines the extension.

The `tenantVerificationResponse` and `verifiedProfessionalPresentation` bind at
least:

- hash and `jti` of the original SMART token;
- index-provider issuer and audience;
- hash of `professionalPresentation` and the unchanged
  `professionalCredential` it contains;
- professional, legal organization and assignment identifiers;
- original subject, purpose and scope without broadening them;
- current assignment, licence, binding and key verification result;
- ledger verification time and opaque evidence references;
- calling EHR as verifier/audience;
- expiry no later than the original SMART token.

The VP and outer introspection JWT are verification evidence, not new access
tokens. The EHR applies the original SMART scope only after validating the
outer tenant signature, its own audience, the nested VP, token correlation and
expiry. A failed verification returns a signed RFC 9701 response with
`token_introspection.active=false` and no VP that could be replayed as positive
evidence.

RFC 7662 and RFC 9701 permit service-specific introspection response members.
The nested `vp_token` member and the federated-proxy role are the explicit
data-space profile layered on those standards; they are not claimed as fields
defined by the base RFCs.

## Optional local token exchange

If a custodian requires a new bearer token addressed directly to its own FHIR
server, it may add OAuth Token Exchange (RFC 8693) after successful `_verify`.
That is a separate profile. It must not extend the original scope or expiry and
must remain linked to the tenant verification evidence.

## Mandatory executable gates

- accept `client_assertion.vp` as the canonical presentation source;
- retain `body.vp_token` during transition;
- reject conflicting nested and sibling presentations;
- preserve the index provider as SMART `aud`;
- preserve or securely resolve the issuance VP from the SMART token;
- authenticate the EHR calling `_verify`;
- reject untrusted provider, invalid signature, expiry and replay;
- reject inactive assignment, licence, binding or signing key independently;
- reject absent or indeterminate ledger evidence instead of defaulting true;
- return the same original professional VC inside a tenant VP bound to the
  exact calling EHR and token hash;
- prove that the VP cannot broaden subject, purpose, scope or expiry;
- prove ordinary Consent and break-glass independently;
- prove the complete local EHR-to-tenant journey without skipped E2E steps.

## Standards and profile boundary

- [RFC 7523: JWT Profile for OAuth 2.0 Client Authentication](https://www.rfc-editor.org/rfc/rfc7523)
- [RFC 7662: OAuth 2.0 Token Introspection](https://www.rfc-editor.org/rfc/rfc7662)
- [RFC 8693: OAuth 2.0 Token Exchange](https://www.rfc-editor.org/rfc/rfc8693)
- [RFC 9701: JWT Response for OAuth Token Introspection](https://www.rfc-editor.org/rfc/rfc9701)
- [OpenID for Verifiable Presentations 1.0](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html)
- [SMART asymmetric client authentication](https://hl7.org/fhir/smart-app-launch/client-confidential-asymmetric.html)

No current standard defines this complete third-party SMART-token-to-tenant-VP
operation. `_verify` is therefore an explicit data-space extension composed
from standard JWT client authentication, VP/VC representation and token
verification principles; it is not presented as a native SMART or OpenID4VP
endpoint.

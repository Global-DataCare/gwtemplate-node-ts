# KMS, ML-KEM and product responsibility boundary

Status: production control specification.

Normative envelope-encryption reference:
[Google Cloud KMS envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption)
and [AWS KMS envelope encryption](https://docs.aws.amazon.com/kms/latest/developerguide/concepts.html#enveloping).

This document records implemented behavior and audit evidence. It is not a
claim that a deployment has passed an external audit.

## Foundation boundary

| Concern | GW Core responsibility | Product responsibility |
| --- | --- | --- |
| Tenant/host root custody | External KMS/HSM KEK and wrapped operational records | Configure deployment/IAM; never supply browser keys |
| Tenant communications | Stable tenant ML-KEM/ML-DSA key pairs and per-message protected transport | Select authorized tenant/subject route |
| Human/device profile PIN | Not owned by GW Core | Trusted UHC/VetChain/SOSChain profile runtime |
| ImagingStudy content encryption | Not implemented or owned here | Future product decision; owner undecided |
| Marketplace, animal insurance, biological traceability | Not GW Core | ConnectHealth VetChain solution |

GW Core must remain sector-neutral. It must not contain UHC PIN policy,
animal-product marketplace policy or ImagingStudy-specific encryption.

## Tenant envelope encryption

The external KMS key is the root and never leaves its provider. A random
32-byte service runtime KEK is provisioned once, encrypted by that root key and
stored only as `KMS_RUNTIME_KEK_CIPHERTEXT`. Every pod independently unwraps it
once during `buildInfrastructure()` using Workload Identity on GCP or temporary
AWS credentials resolved by the AWS SDK credential chain, and keeps its own
plaintext copy only in process memory.

The runtime KEK, not the external KMS, wraps five records per host/tenant and version:

- communication signing key,
- VC signing key,
- ML-KEM communication private key,
- confidential-storage operational key,
- protected-index HMAC key.

The host and each tenant are sibling `entityVaultId` security contexts; they
are not a chain of nested vault keys. The host storage DEK protects host-scoped
confidential documents. A tenant storage DEK protects documents stored in that
tenant context, including its employees and other tenant-owned records. The
host storage DEK never wraps tenant DEKs: the process runtime KEK wraps every
host and tenant operational-key record directly.

The single bootstrap KMS request binds `KMS_RUNTIME_KEK_ID` plus
`service-runtime-kek-v1` as authenticated context. Each local tenant envelope
then binds `entityVaultId + purpose` as AES-GCM AAD.
Production rejects `memory` and raw `KEK_SECRET` custody and requires
`gcp`, `aws` or `hashicorp-transit`. `KMS_KEY_ID` names a rotatable
GCP CryptoKey or AWS KMS Key. A GCP value must not pin a CryptoKeyVersion; AWS
accepts the key ARN/id or alias forms supported by KMS.

`npm run kms:provision-runtime-kek` performs the one-time KMS encrypt used to
create the deployment ciphertext. Each pod start performs exactly one KMS
decrypt. Tenant provisioning performs five local AES-GCM wraps and rehydration
performs five local unwraps for the atomic keyset. The unwrapped keyset lives in
the bounded in-process cache controlled by:

- `KEY_MATERIAL_CACHE_TTL_MS` (default 300000),
- `KEY_MATERIAL_CACHE_MAX_ENTRIES` (default 1024).

Changing operation purpose does not reload the same keyset. Expiry, eviction,
rotation, restart or a pod without the cached tenant can trigger local
rehydration. No tenant business operation calls the external KMS.

### AWS deployment configuration

Use a symmetric `ENCRYPT_DECRYPT` KMS Key and prefer its stable key ARN:

```dotenv
KMS_PROVIDER=aws
KMS_REGION=eu-west-1
KMS_KEY_ID=arn:aws:kms:eu-west-1:111122223333:key/00000000-0000-0000-0000-000000000001
KMS_RUNTIME_KEK_ID=gw-production
KMS_RUNTIME_KEK_CIPHERTEXT=<output-from-provisioning-command>
```

Run `npm run kms:provision-runtime-kek` once with an operator/provisioning
identity allowed to call `kms:Encrypt`. Store its printed
`KMS_RUNTIME_KEK_CIPHERTEXT` in the deployment secret. The GW pod identity
requires `kms:Decrypt` on that exact key. `KMS_REGION` selects the KMS endpoint;
it does not authenticate the pod and must match the region of `KMS_KEY_ID`.
The physical region of the Kubernetes cluster does not determine the KMS key
region.

Authentication depends on where Kubernetes runs:

- On EKS, Pod Identity or IRSA can supply temporary credentials to the normal
  AWS SDK credential chain.
- For Kubernetes hosted outside AWS, EKS-only mechanisms do not apply. The
  default production choice is IAM Roles Anywhere: configure a trust anchor,
  profile and runtime IAM role; mount an X.509 workload certificate and its
  private key through the cluster's secret-delivery mechanism. For the
  long-running GW process, run the official helper as a pinned, integrity-checked
  `serve` sidecar in the same pod and set
  `AWS_EC2_METADATA_SERVICE_ENDPOINT=http://127.0.0.1:9911` on the GW container.
  The helper exchanges the certificate for temporary credentials, keeps them
  in memory and refreshes them before expiry. Only trusted containers may share
  that pod because each container can reach the local credential endpoint. A
  mounted AWS config using `credential_process` is an alternative when the
  helper executable is deliberately included in the GW container.
- If the external cluster deliberately publishes a stable HTTPS OIDC issuer,
  discovery document and JWKS, it may instead use an IAM OIDC provider plus a
  projected service-account token. Scope the role trust to the exact token
  audience, namespace and service account, then provide `AWS_ROLE_ARN` and
  `AWS_WEB_IDENTITY_TOKEN_FILE` to the SDK. This is web-identity federation,
  not IRSA.

Do not inject long-lived AWS access keys. The runtime role and the KMS key
policy must allow only `kms:Decrypt` on the selected key. Keep the provisioning
identity with `kms:Encrypt` separate. The external cluster also needs outbound
TLS connectivity to the selected AWS credential endpoint and the regional KMS
endpoint. Bootstrap must fail before readiness if temporary credentials cannot
be obtained or KMS decrypt is denied.

AWS references:

- [IAM Roles Anywhere for workloads outside AWS](https://docs.aws.amazon.com/rolesanywhere/latest/userguide/introduction.html)
- [IAM Roles Anywhere credential helper modes](https://docs.aws.amazon.com/rolesanywhere/latest/userguide/credential-helper.html)
- [AWS SDK web-identity credentials](https://docs.aws.amazon.com/sdkref/latest/guide/access-assume-role-web.html)

Both provisioning and bootstrap bind the exact
`entityVaultId=KMS_RUNTIME_KEK_ID` and
`purpose=service-runtime-kek-v1` encryption context. A different context fails
closed. Normal tenant operations use the unwrapped runtime KEK locally and do
not need `kms:Encrypt`.

Upgrade compatibility: on the first load of a legacy record that was wrapped
directly by KMS, GW uses the root adapter once and immediately persists the same
record as an `rkek1` local envelope. Audit logs can therefore show five extra
decrypts per legacy tenant during the controlled cutover only.

Pods share durable ciphertext and identifiers only. They do not share plaintext
KEKs, a distributed singleton or a mandatory cache. If bootstrap KMS decrypt
fails, the pod must not become ready. Normal provider key rotation needs no
tenant re-encryption while the provider retains decrypt support for the key
version recorded in the runtime-KEK ciphertext.

### HashiCorp Transit deployment configuration

`KMS_PROVIDER=hashicorp-transit` provides the open-source, self-hosted root
custody option. `KMS_KEY_ID` identifies the Transit key, while
`HASHICORP_TRANSIT_BASE_URL`, `HASHICORP_TRANSIT_MOUNT_PATH`,
`HASHICORP_TRANSIT_TOKEN` and the optional `HASHICORP_NAMESPACE` select and
authorize the Transit engine. The same `KMS_RUNTIME_KEK_ID` and
`KMS_RUNTIME_KEK_CIPHERTEXT` runtime configuration applies.

The provisioning identity needs Transit encrypt capability for the selected
key. The runtime identity needs Transit decrypt capability. A production token
must be supplied through the deployment secret mechanism, scoped to that path,
and must not be embedded in an image or source-controlled environment file.

## Deployment audit: call volume, cost, and security

The production call model is provider-neutral. Provisioning a new runtime KEK
performs one external encrypt operation. Bootstrap performs one external
decrypt operation per pod or process start. Normal host and tenant business
operations make no external KMS or Transit calls because operational key
records are wrapped and unwrapped locally with the process-owned runtime KEK.

This makes deployment cost predictable without freezing commercial prices in
the specification. Estimate it from active root-key custody plus billable
cryptographic request volume. For a stable runtime KEK, that volume is
proportional to successful pod or process starts, including rolling
deployments, autoscaling replacements and restarts. A restart loop is therefore
both an availability signal and a possible source of avoidable external calls.
Self-hosted Transit additionally carries the infrastructure and operational
cost selected by the operator for its Vault deployment.

Security and cost evidence for a deployment must demonstrate:

1. one provisioning identity allowed to encrypt a new runtime KEK;
2. a separate runtime identity limited to decrypting that runtime KEK;
3. one successful bootstrap decrypt for each started pod or process;
4. no unexpected external cryptographic operations during ordinary host or
   tenant traffic;
5. alerts and investigation for restart loops or external-call growth;
6. separately identified one-time decrypts for legacy direct-root envelopes
   during a controlled migration.

Provider invoices or calculators may be attached to an environment-specific
evidence pack, but monetary values and provider comparisons are not part of
this portable GW CORE specification.

## Tenant ML-KEM

The tenant ML-KEM key pair is a communication identity, not the KMS root and not
the tenant storage KEK. Its public key can be published in DID/JWKS material;
its private key remains in the wrapped tenant key records.

Current protected transport creates fresh encapsulation randomness and a fresh
shared secret/CEK for each single-recipient JWE. GW does not currently expose
the historical Kyber multi-recipient construction that encrypts content once
with one AES CEK and wraps that CEK independently into `recipients[]`.

## Explicitly deferred

A future ImagingStudy may use one content CEK for an explicitly defined study
or study version, with a unique AES-GCM IV and instance-bound AAD per encrypted
instance. Its CEK may be wrapped to one storage ML-KEM recipient or later to
several recipients without re-encrypting content.

That is not implemented here. It must not be inferred from the tenant
`storage` record, described as current capability, or assigned to GW Core
until a product owner and executable specification are approved.

## Audit evidence

A production evidence pack must contain:

1. deployment configuration showing external envelope custody,
2. IAM grant limited to the runtime service identity and exact root key,
3. provider audit logs for encrypt/decrypt and administrative changes,
4. enabled key-version/rotation policy and incident procedure,
5. `npm run kms:audit` output with no missing wrapped records,
6. tests proving production rejects memory/local custody,
7. tests proving one KMS decrypt at bootstrap and local tenant wrap/unwrap,
8. proof that plaintext operational keys are absent from persisted records,
9. pod restart/readiness plus provider key-version rotation drill results.

Never state “audit passed” without the external report and deployment-specific
evidence.

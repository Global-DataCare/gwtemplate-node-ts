# Secure profile enrollment

> 101 note
> - Applications call one high-level SDK method.
> - GW CORE verifies the protected message and its authorization proofs.
> - Application code does not build JOSE envelopes, HTTP routes or worker jobs.

## What the application does

After the user has authenticated and received an activation code, the BFF asks
the SDK profile-session manager to enroll the protected profile:

```ts
const profile = await profileSessions.enroll(enrollment);
```

`enrollment` is the typed `ServerProfileEnrollmentInput` already assembled by
the application. The SDK performs the activation-code exchange and device
registration. See the copyable snippet in
[`secure-profile-enrollment.ts`](../snippets/secure-profile-enrollment.ts).

The application receives an enrolled profile. It does not need to know whether
the selected runtime used the local plaintext test transport or encrypted
DIDComm transport.

## What GW CORE guarantees

GW CORE applies independent checks in this order:

1. Open the encrypted transport when one is present.
2. Verify the inner message signature.
3. Decide whether the signing key is an allowed bootstrap key or a registered
   actor key.
4. Verify the authorization proof for the operation.
5. Queue only the verified claims needed by the worker.

An embedded public key proves only that the sender owns the matching private
key. It grants no authority by itself.

Before device registration, the organization/controller bootstrap and first
Offer acceptance may use their verified bootstrap communication key. The first
device registration then verifies possession of the new device key carried by
the signed request, while the already-verified controller and host-issued
initial access token authorize registering it. After registration, GW CORE
resolves the persisted actor/device keys; an arbitrary embedded key cannot
replace them.

Legacy `Organization/_activate` does not replace DCR in the current contract:
it does not create the `DeviceProfile`, issue the OAuth `client_id`, or bind the
device to its licence. Those are device-registration responsibilities.

## Why the initial access token matters

The initial access token is short lived and belongs to the activation flow. GW
CORE verifies it for both local plaintext and encrypted device registration.
Only claims returned by that server-side verification enter the asynchronous
job; request-body claims never replace them.

## Local-first verification

Use separate local ports for each GW and ICA. Portal and telephone-assistant
journeys can run with test adapters and in-memory persistence when they do not
need ledger evidence. Use Fabric `local-network` only for journeys that must
prove durable ledger traceability. Promote the same tested image to
`test-network` only after those local journeys pass.

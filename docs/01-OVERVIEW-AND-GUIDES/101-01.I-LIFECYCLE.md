## Lifecycle 101

> 101 note
> - Teach here: GW CORE backend contract and lifecycle semantics after the caller already has a loaded profile/session/actor facade from an SDK or app runtime.
> - Do not present GW as the first login/profile entrypoint for self-managed users.
> - Read [101-README.md](./101-README.md) for the ordered path and upstream runtime entrypoints.

Status: Current guidance for GW CORE lifecycle semantics and SDK alignment.

This document is the local "101" for lifecycle semantics in GW CORE. It does not replace shared examples from `gdc-common-utils-ts`, but it explains the rules that SDK prompts and GW maintainers should treat as the stable model for this repository.

Current canonical user-story boundary:

- login/profile load/session bootstrap live upstream in `gdc-sdk-front-ts` or `gdc-sdk-node-ts`
- GW begins after that point, when an already-authenticated actor submits one request
- GW docs should therefore teach route/contract/lifecycle semantics, not the first user-login story

## Scope

This document covers:

- individual lifecycle in GW CORE
- employee lifecycle in GW CORE
- hosted tenant authorization lifecycle in GW CORE
- read-only clinical-summary lifecycle
- how `status`, `audit`, and blockchain-facing lifecycle projections should relate

This document does not define extension-domain actions for products, genomics, or other future repositories.

## Core rules

- `_search` uses search parameters or search claims.
- `_batch + POST` creates a resource.
- `_batch + PUT` updates resource data.
- `_batch + PATCH` performs lifecycle transitions or other partial operational updates.
- `/_purge + POST` is an explicit business command, not generic CRUD.
- `DELETE` must not be used as the semantic model for `disable`.

Mental model:

- change email, phone, name, occupation: `PUT`
- disable or enable a resource: `PATCH`
- mark a resource as archived or soft-deleted: `PATCH`
- release licenses and preserve traceability: `/_purge`

## Canonical storage model

- `ConfidentialStorageDoc.status` is the canonical current status.
- `ConfidentialStorageDoc.content` stores the business resource and claims.
- `ConfidentialStorageDoc.audit` stores metadata about the latest relevant change.
- blockchain should receive a derived lifecycle event, not the raw confidential storage document.

`status` is the source of truth. `audit` must describe the transition, not compete with `status`.

## Audit guidance

`audit.deactivated` is too weak for a lifecycle domain that can include:

- `pending`
- `active`
- `inactive`
- `purged`
- `suspended`
- `revoked`

GW CORE should keep `status` as the canonical field and extend `audit` with transition metadata instead of duplicating the current status value.

Recommended audit fields:

- `audit.updated`
- `audit.statusChangedAt`
- `audit.statusChangedBy`
- `audit.previousStatus`
- `audit.statusReason`

`audit.status` is not recommended as a primary field because it duplicates `status` and introduces drift risk.

## Derived blockchain event

When lifecycle changes must be anchored or projected to blockchain, the event should be derived from `status` plus audit transition fields.

Example:

```json
{
  "resourceId": "…",
  "resourceType": "…",
  "previousStatus": "active",
  "status": "inactive",
  "changedAt": "2026-05-26T12:00:00Z",
  "changedBy": "did:example:actor",
  "reason": "manual-disable"
}
```

Source mapping:

- `status` from `ConfidentialStorageDoc.status`
- `previousStatus` from `audit.previousStatus`
- `changedAt` from `audit.statusChangedAt`
- `changedBy` from `audit.statusChangedBy`
- `reason` from `audit.statusReason`

## Payload conventions

- Prefer `resource.id` as the resource locator when available.
- `resource.identifier` can be used when the domain contract defines it clearly.
- `resource.meta.claims` is the canonical carrier for resource business claims.
- Do not model `PATCH` or `/_purge` as internal `_search` operations with query-style URL parameters.

## GW CORE lifecycle semantics

### Individual / family

- `individual/org.schema/Organization/_disable`
  - disables the hosted individual/family registration
  - does not release licenses
- `individual/org.schema/Organization/_purge`
  - requires the registration to be inactive first
  - releases or disassociates licenses
  - preserves the individual/family record for traceability

### Employee

- employee disable must not release licenses
- employee purge requires inactive status first
- employee purge releases or disassociates licenses and preserves the employee record for traceability

### Hosted tenant authorization

- tenant authorization `disable` is a local suspension signal
- tenant authorization `enable` reactivates the local authorization state
- this is not the same as credential revocation
- this is not an implicit license release

## Communication note

For mutation lifecycle commands, `Communication` is not the canonical execution
mechanism. Those commands act directly on the target resource.

For mutations:

- lifecycle commands should be modeled directly on the target resource
- `Communication` may later become a transport or evidence envelope for those commands
- future extension repositories may reuse the same lifecycle base and then wrap it in conversational or production-thread flows

This rule does not apply to the read-only clinical-summary lifecycle.
`Communication` is the canonical auditable request envelope for
`Subject/$summary`.

## Digital Twin secondary-use lifecycle

The patient portal exposes only an enabled/disabled setting. Its authenticated
BFF resolves the operational subject and the organization/tenant that provides
the index, then submits one FHIR `Consent` through `resource.meta.claims` and
`entry.meta.claims`. The rule uses purpose `HRESCH`, the canonical Digital Twin
reader action and `permit` or `deny`; it has no ODRL attachment and does not
accept a research organization from the browser.

The BFF creates the Consent identifier exactly once as a random `urn:uuid` in
the server-side index-enrollment transaction, persists it with that enrollment
and reuses it for status, permit and deny. It is not derived from the subject or
tenant DID and is not browser state. Study-specific permissions are separate
FHIR Consent resources with their own identifiers and research actors.

Operational IPS data continues to enter through
`individual/.../Communication/_batch`. GW alone projects one Composition per
IPS document/version, containing all its sections, and assigns a registered
pseudonymous `urn:uuid` subject from the tenant-private alias. A patient portal
must never split an IPS into one Composition per section or publish canonical
records through `digitaltwin/.../Composition/_batch`.

`deny` pauses synchronization and preserves both the alias and anonymous
published data. A later `permit` reuses the alias and rebuilds from current
operational data. Provider offboarding purge removes only the private
operational-subject to twin correspondence; it never deletes anonymous research
data or immutable audit anchors.

## Clinical summary read lifecycle

This flow reads the data already available for an individual. It does not
ingest, import or update the subject index.

1. an SDK actor facade receives `subjectId`, `requesterId` and optional section
   filters
2. it sends one canonical claims-first `Communication`
3. `resource.meta.claims` contains the `Subject/$summary` operation reference
   and attached serialized FHIR `Parameters` with subject, document type and
   repeated section filters; a native FHIR projection may represent these as
   `payload.contentReference` and `payload.contentAttachment`
4. GW executes `$summary`
5. GW returns an authoritative FHIR `Bundle` document
6. the SDK exposes that Bundle as `ClinicalSummaryReadResult`

The same read applies after either write boundary:

- after `updateClinicalSection(...)`, `$summary` consolidates the available
  section projections into a document and returns the indexed resources
- after `updateClinicalSummary(...)`, `$summary` returns the consolidated
  multi-section document
- `Composition/_search` and `searchClinicalBundle(...)` return index/search
  records and are not the resource-read API

For an individual self-read, `subjectId` is always the selected individual's
DID. `requesterId` identifies the authenticated actor: it is the same DID for
true self access and the provider/controller DID for delegated access.

Both API and R4 Communications are supported. GW executes API jobs directly
from canonical `resource.meta.claims`; it does not manufacture a native FHIR
payload or select an R4 version first. The returned API document retains the
native Composition section graph so SDK readers can resolve the claims-first
clinical entries.

An EHR can submit native FHIR resources without `resource.meta.claims`. Before
indexed persistence, GW converts those native resources through the shared
FHIR-to-claims normalizer. Existing claims take precedence when both shapes
are present. For a native section-only batch, the Communication carries the
section in native FHIR `Communication.topic` (the canonical claims key is
`Communication.topic`); a document Bundle carries its own Composition section
graph. `payload.contentCodeableConcept` is a coded payload and is not the
section discriminator.

`Composition.section` on each indexed clinical resource is authoritative for
reconstructing that graph. Resource type alone is insufficient: `Observation`
is used by results, vital signs, social history and pregnancy history, while
`Condition` is used by current problems, functional status and past illness.
GW therefore selects records by both the section token and resource family.
The all-sections regression fixture additionally proves that `Flag` remains in
alerts and `DeviceUseStatement` remains in medical devices.

Omitting `filterSections` requests all sections available to the actor.
`section=*` belongs to SMART permission matching and is not sent as the
application-level `$summary` section filter.

For an individual member or professional request, GW loads the authoritative
Consent rules and calls the shared `deriveGrantedSmartScopes(...)` projection.
It signs only the explicit `requested ∩ consented` Composition read scopes.
Invitation acceptance, contact linkage or successful card resolution alone
never authorizes clinical data, and a multi-subject or write-bearing request
fails closed.

Application code calls:

```ts
const summary = await sdk.requestClinicalSummary(tenantContext, {
  subjectId,
  requesterId,
  filterSections: [allergySection],
});
```

It then consumes:

```ts
const sections = summary.reader.getDocumentSections();
const sectionCount = summary.reader.getDocumentSectionCount();
const declaredCount =
  summary.reader.getDocumentSectionResourceCount(allergySection);
const entries = summary.reader.getDocumentSectionResourceEntries(
  allergySection,
);
const totalEntryCount = summary.reader.getEntryCount();
const visibleResourceCount = summary.reader.getVisibleResourceCount();
const visibleResourceIds = summary.reader.getVisibleResourceIds();
const allergyView = summary.document
  .filterBySections([allergySection])
  .filterByTypes([ResourceTypesFhirR4.AllergyIntolerance])
  .filterByClinicalDateRange('2026-01-01', '2026-12-31');
const resources = allergyView.getResources();
const filteredCount = allergyView.getResourceCount();
```

Reader responsibilities:

- `BundleReader`: sections, declared counts, references, IDs and Bundle entries;
  its visible helpers exclude flattened native FHIR `contained[]` children
  from top-level UI navigation, while total entries remain available for audit
  and FHIR reconstruction
- `FhirDocumentFacade`: resolved FHIR resources and section/type/date filters
- `LifecycleResultReader`: operation statuses/issues only, never clinical
document navigation

Structural visibility is not active/inactive clinical status.

`ingestCommunicationAndUpdateIndex(...)` is a write/projection operation and
must not be called by a screen or channel that is reading `$summary`.

## SDK guidance

SDK prompts should follow this order:

1. Read this document for stable lifecycle semantics.
2. Read `docs/90.L-LIFECYCLE_CURRENT_VS_TARGET.md` to distinguish current GW behavior from target normalization.
3. Read `CHANGELOG.md` to identify what has already shipped in the current version.

SDKs should prioritize the current deployed GW CORE contract, while leaving explicit TODOs for the target normalized `PATCH` model where the backend has not migrated yet.

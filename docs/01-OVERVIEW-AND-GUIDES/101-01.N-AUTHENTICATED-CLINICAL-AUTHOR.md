# Authenticated clinical author

Applications use the high-level actor facade to add, import, update or remove
health information. The BFF supplies the authenticated session; UI code does
not construct DIDComm, JOSE, queue jobs or storage records.

The acceptance journeys are numbered and share one persistence contract:

1. An administrative professional imports an external IPS; GW preserves its
   external author/attester and records the employee only as submitter.
2. An individual controller creates a neutral fact; its RelatedPerson urn:uuid
   is both author and personal attester.
3. A caregiver creates another neutral fact; its distinct RelatedPerson
   urn:uuid is both author and personal attester.
4. A professional creates provider content; the jurisdictional CDS legal
   organization URN is author and PractitionerRole urn:uuid is attester.
5. `$summary` aggregates the facts and emits resolvable Organization,
   Practitioner, PractitionerRole and RelatedPerson graph entries.
6. `PUT`/`DELETE` authorization checks the stored assignment attester; sharing
   an owner never silently grants deletion.

For information created locally, the protected creator binding determines the
FHIR provenance. It is not correct to apply a blanket
`Composition.author = actorDid` rule. These are the canonical cases:

| Authenticated profile and source of the content | `Composition.author` | `Composition.attester.party` |
| --- | --- | --- |
| Individual records their own content without a member assignment | Stable individual reference | Same personal reference when no distinct attester is supplied |
| Member/controller/caregiver records content created or dictated by the individual | Stable individual reference | Registered `RelatedPerson` urn:uuid |
| Member/controller/caregiver creates the content | Registered `RelatedPerson` urn:uuid | The same `RelatedPerson` urn:uuid |
| Professional/employee records provider content | Stable legal organization URN (`urn:cds-<jurisdiction>:v1:organization:<type>:<value>`) | Registered `PractitionerRole` urn:uuid |
| Administrative professional imports an external IPS | Preserved external author | Preserved external attester; the importer remains only submitter |

`ClinicalSourceAuthorSelections.Owner | Creator` remains a rolling compatibility
input but cannot accept a FHIR reference. High-level clone/section helpers
derive the table above from the exact binding already stored in the protected
profile. A browser field, request body, stable contact alias, DIDComm sender or
signing key cannot choose either identity.

Authorship and correction authority are separate. For `PUT`, another active
member/controller/caregiver assignment owned by the same individual may create
a corrected version. An authenticated professional assignment authorized by
the tenant's clinical-write service may also correct personal content. The new
version uses the provenance that reflects its real source: an individual or
organization remains author when the actor only transcribes its correction;
an individual member who supplies the correction uses its RelatedPerson as both
author and attester. A professional correction remains authored by its stable
legal organization URN and attested by its PractitionerRole. A professional assignment from a different,
unauthorized provider is not admitted merely because it has a clinical role.
These successor rules do not authorize `DELETE` and never rewrite an earlier
version or its evidence.

For a direct `updateClinicalSummary(...)`, applications use these identities:

- `subject`: the individual DID;
- `sender`: the operational `session.actorDid` returned with the authenticated
  role-specific profile, never a multibase URN or a DID/alias owned by the portal;
- `recipient`: the real provider-tenant DID inside the host that accommodates
  that tenant, never the host DID or a portal alias;
- `Composition.author` and `Composition.attester`: obtained by the BFF through
  `ServerProfileSessionManager.exportClinicalCreatorIps(...)`, not from UI
  fields;
- audit submitter and signing key: derived from the authenticated DIDComm
  request and its verified `kid`, independently of the FHIR provenance.

The operational `actorDid` proves the transport actor and selects the protected
binding. It is not copied into `Composition.author`; the resulting author is
the owner or registered FHIR assignment selected above. It can only be the same
string if that exact value is already the registered FHIR reference, which GW
must verify rather than assume.

This is the same contract for an individual controller, an individual
member/caregiver and a professional. Each role-specific loaded profile returns
its own `ActorSession`; only the concrete actor DID and capabilities differ.

The operational DIDs are always produced by shared builders, never by manually
joining or hashing strings in a portal:

```ts
// Employee/professional template:
// did:web:<organization-domain>:employee:<multibase-contact-hash>:<role-token>
// Concrete shared test value:
// did:web:api.acme.org:employee:zW1pca8dQVVz2apBk8A1CWJ8VSHgheXpRZoZtqwhnkHjFkV:ISCO-08|2211
const employeeDid = buildProfessionalDidWeb({
  organizationDidWeb: EXAMPLE_API_ORGANIZATION_DID,
  email: EXAMPLE_EMAIL_PROFESSIONAL,
  role: EXAMPLE_HEALTHCARE_ACTOR_ROLE_GENERALIST_MEDICAL_PRACTITIONER,
});

// Individual member/controller template:
// did:web:<provider-path>:individual:<secure-id-type>:<secure-id-value>:member:<secure-member-value>:<role-value>
const controllerDid = buildIndividualMemberDidWebFromPrivateIdentifiers({
  providerDidWeb: EXAMPLE_HOSTED_PROVIDER_DID,
  secureIdTypeIndividual: SecureIdTypesIndividual.Uuid,
  privateIdValueIndividual: EXAMPLE_PRIVATE_INDIVIDUAL_UUID,
  secureIdTypeMember: SecureIdTypesIndividual.Email,
  privateIdValueMember: EXAMPLE_EMAIL_CONTROLLER_INDIVIDUAL,
  roleType: EXAMPLE_INDIVIDUAL_CONTROLLER_ROLE_TYPE,
  roleValue: EXAMPLE_INDIVIDUAL_CONTROLLER_ROLE_VALUE,
});
// did:web:host.example.com:health-care:organization:taxid:ES-B00112233:individual:UUID:zG9H82pae9SCXvec3D4YKqhX8bj8F1mRgzxMEdwXXonT7BWsvsUiP2u52sWQTeESpoMee:member:zG9FEVaXcQgzppJZUe7WwnqbM1mqTLbktoPSbPvMj2T6fj121vncQCbKyqh4BTYtSh2Tj:RESPRSN
```

Both private-identifier components use SHA3-384 multihash/base58btc. The role
type stays in protected authorization data; only its value is serialized.

For professional FHIR authorship, GW instead uses the legal organization
identifier `urn:cds-es:v1:organization:tax:ES-B00112233`, built by
`buildOrganizationAuthorizationUrnCds(...)`. It contains jurisdiction and
grammar version but no host/domain. It is not the older
`urn:cds-<jurisdiction>:<org>:<contact>:<role>` role-license preimage (which is
hashed into a seat id), nor the `urn:cds:<jurisdiction>:v1:...` identifier of an
Offer/Order.

The corresponding stable employee authorization identity keeps an explicit
member marker:
`urn:cds-es:v1:organization:tax:ES-B00112233:member:zG9Gjhm4F9WwjUbk4D2sAL1wDj5MWuXsJooWPYDG5XYKURBQa4Q7wXttzusFntw6tXH3F:ISCO-08|2211`.
It is built by `buildOrganizationMemberAuthorizationUrnCds(...)`; it is not a
substitute for the professional's FHIR PractitionerRole `urn:uuid`.

For an editable demonstration copy of an imported IPS, the BFF passes the
complete protected `clinicalCreator` export to
`cloneImportedClinicalDocumentForDemo(...)`. The helper assigns new resource
ids and applies the same table: legal organization URN plus PractitionerRole
for a professional; one RelatedPerson urn:uuid as both author and attester for
a member/controller. It never makes the loaded session `actorDid` the author
and never rewrites the source document.

An imported IPS may name an external `urn:*` author. That value is source
provenance, not permission granted to the importer. Importing or repeating the
same URN does not allow the local account to rewrite or delete source-authored
facts; replacement needs independently verified source evidence.

The protected actor profile also keeps a stable clinical-creator binding. It
contains the imported or generated UUID of the member/Practitioner, a distinct
UUID for the current relationship or professional assignment, its owner and
its governed role. Phone, email, operational actor DIDs, registered DCR clients
and signing keys are aliases of that binding, not the permission identity.
The employee/member import or onboarding process creates the stable binding
first. DCR may then carry that exact binding so GW can verify it and attach the
new client and public-key aliases; DCR never gets to invent the UUIDs or role.

Consequently, `$summary` exports locally authored data with ordinary FHIR
references. The professional source uses its stable legal organization URN and
PractitionerRole; a member/controller-created version uses its RelatedPerson as
author and attester. ONESELF refers to the existing subject, not controller
authority. The permission actor is the assignment UUID plus the role.
Here, “assignment” means GW's technical Occupation or relationship record. It
does not model an employment or caregiver contract. GW currently supports
activate/deactivate lifecycle only; contract periods and renewals are outside
this scope.

Consent, RelatedPerson and clinical resources follow the same rule when they
are carried through the normal Communication ingestion flow. Every projected
confidential resource indexes the sector and the governed Composition
provenance. Multi-valued author or attester claims produce repeated indexed
attributes, while the verified sender and signing key remain audit fields.

For a section `batch` or `collection`, the BFF places this resolved
`Composition.author`/`Composition.attester` provenance in the attached
`Bundle.meta.claims`. GW copies it into every persisted confidential resource
and into the generated Composition projection. A later `$summary` rebuilds the
native FHIR `Composition.author` and `Composition.attester` graph, including the
registered `RelatedPerson` or `PractitionerRole` resources. CSV values in flat
claims are positional and become repeated indexed attributes; empty attester
mode/time positions stay aligned with their attester reference.

For every successful confidential resource version, GW computes its canonical
CID. One Communication-carried Bundle is submitted as one sanitized
primary-document `data[]` batch with one evidence entry per resource. The
governed evidence service processes the complete array inside one transaction and writes
each resource CID as that version's individual `assetId`; it does not preserve
the input primary document as an aggregate asset. Entries contain only resource
type, CID/version id and optional `meta.tag[]` values sanitized through the
positive ledger-safe allowlist (`id`, `system`, `code`, `version` and
`userSelected`). Displays, free text and unknown tag fields are removed again at
the ledger boundary. The original `resource.meta.claims` object is not accepted
as ledger metadata, even when it appears to contain only codes: publication
uses the smaller `meta.tag[]` contract.

The same per-resource asset carries historical `relationships` and
`ownerships`, but only as SHA3-384 multihashes. When a reference contains the
stable UUID of an organization, employee assignment, `PractitionerRole` or
subject, GW removes UUID punctuation, decodes the hexadecimal value to its
canonical 16 bytes and hashes those bytes. Thus a bare UUID, `urn:uuid:...`, a
FHIR `Type/<uuid>` reference and an employee URN ending in
`:instance:<uuid>` produce the same opaque link. Non-UUID references hash their
canonical UTF-8 form. Relationship
sets distinguish author, attester, custodian, Communication sender, verified
submitter and signing key. Ownership hashes the subject. Multiple CSV authors
or attesters become multiple opaque values. This lets chaincode compare and
audit provenance without receiving the raw DID, URN, URL, key id or contact.
The resource CID binds canonical protected content; the Fabric transaction
immutably binds that CID to these opaque relationship and ownership fields.
`fullUrl`, raw identities, the complete claims object and clinical payloads do
not enter the ledger. The
asynchronous response exposes each CID/asset id and their shared Fabric
transaction id. In local
`networkKind=test` the memory adapter returns a synthetic transaction id; only
a Fabric-backed environment proves an on-chain transaction. The BFF supplies
only the authenticated clinical operation and its domain context. GW chooses
the governed ledger route internally; callers and deployment configuration do
not provide channel or smart-contract names.

The employee, role, licence and device-key graph behind an employee link is
specified in
[`28-clinical-employee-ledger-schema.md`](../../docs-v2/28-clinical-employee-ledger-schema.md).
Those records remain separate: the clinical asset does not duplicate an
employee role, licence, JWK or lifecycle dates.

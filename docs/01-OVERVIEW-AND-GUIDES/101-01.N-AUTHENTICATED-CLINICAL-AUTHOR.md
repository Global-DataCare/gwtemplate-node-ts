# Authenticated clinical author

Applications use the high-level actor facade to add, import, update or remove
health information. The BFF supplies the authenticated session; UI code does
not construct DIDComm, JOSE, queue jobs or storage records.

For information created locally, the recorded author is the authenticated
actor DID. A browser field, request body or stable contact
`urn:multibase:z...` alias cannot choose a different author. Only that author,
or the same person reached through a privately verified linked login, may
later update or remove the fact. Professional roles and individual-member
roles remain part of the operational DID/credential contract; they are never
inferred from the stable contact alias.

For a direct `updateClinicalSummary(...)`, applications use these identities:

- `subject`: the individual DID;
- `sender`: the operational `session.actorDid` returned with the authenticated
  role-specific profile, never a multibase URN or a DID/alias owned by the portal;
- `recipient`: the real provider-tenant DID inside the host that accommodates
  that tenant, never the host DID or a portal alias;
- `Composition.author`: the same session `actorDid` for locally editable data.

This is the same contract for an individual controller, an individual
member/caregiver and a professional. Each role-specific loaded profile returns
its own `ActorSession`; only the concrete actor DID and capabilities differ.

For an editable demonstration copy of an imported IPS,
`cloneImportedClinicalDocumentForDemo(...)` assigns new resource ids and sets
the copy's `Composition.author` to the loaded session's `actorDid`. It does not
rewrite the source document.

An imported IPS may name an external `urn:*` author. That value is source
provenance, not permission granted to the importer. Importing or repeating the
same URN does not allow the local account to rewrite or delete source-authored
facts; replacement needs independently verified source evidence.

The protected actor profile also keeps a stable clinical-creator binding. It
contains the imported or generated UUID of the member/Practitioner, a distinct
UUID for the current relationship or professional assignment, its owner and
its governed role. Phone, email, operational actor DIDs, registered DCR clients
and signing keys are aliases of that binding, not the permission identity.
The employee/member import or onboarding process creates the stable binding
first. DCR may then carry that exact binding so GW can verify it and attach the
new client and public-key aliases; DCR never gets to invent the UUIDs or role.

Consequently, `$summary` exports locally authored data with ordinary FHIR
references: a personal relationship becomes RelatedPerson; a professional
assignment becomes PractitionerRole plus Practitioner; ONESELF refers to the
existing subject. The permission actor is the assignment UUID plus the role.
A new contract can receive a new assignment UUID without changing the UUID of
the underlying person.

Consent, RelatedPerson and clinical resources follow the same rule when they
are carried through the normal Communication ingestion flow.

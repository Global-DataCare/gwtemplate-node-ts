# Shared Bundle Entry Editors In GW

This note exists to remove ambiguity between:

- what `gdc-common-utils-ts` documents in its internal/editor 101 guides
- what the currently installed shared package actually exposes in this GW repo

Canonical shared references:

- [`101-BUNDLE_EDITOR_READER.md`](https://github.com/Global-DataCare/gdc-common-utils-ts/blob/main/docs/101-BUNDLE_EDITOR_READER.md)
- [`101-VITAL_SIGN_ENTRY_EDITOR.md`](https://github.com/Global-DataCare/gdc-common-utils-ts/blob/main/docs/101-VITAL_SIGN_ENTRY_EDITOR.md)
- [`101-IPS_BUNDLE.md`](https://github.com/Global-DataCare/gdc-common-utils-ts/blob/main/docs/101-IPS_BUNDLE.md)

## Current Contract In This Repo

With the shared package version currently installed by GW, the public typed
clinical entry editors available here are:

- `BundleEntryEditor.asVitalSign()`
- `BundleEntryEditor.asObservation()`

GW does **not** currently consume published typed entry editors here for:

- `asAllergy()`
- `asMedicationUseStatement()`
- `asMedicationStatement()`
- `asCondition()`

That is why GW tests and docs can show the vital-sign chaining style directly,
but they do not currently show the same `asX()` pattern for allergies,
medications, or conditions: that public editor surface is not present yet in
the installed shared dependency.

## What To Show In GW Today

For GW-local examples and tests, use this split:

- bundle mechanics and entry counting: `BundleEditor` and `BundleReader`
- vital-sign authoring: `newEntry(...).asVitalSign()`
- general Observation authoring: `newEntry(...).asObservation()`
- AllergyIntolerance / MedicationStatement / Condition: generic
  `BundleEntryEditor.setClaim(...)` and `getClaim(...)`

Short example:

```ts
import { BundleEditor } from 'gdc-common-utils-ts/utils/bundle-editor';
import { BundleReader } from 'gdc-common-utils-ts/utils/bundle-reader';
import { EmployeeBundleOperations } from 'gdc-common-utils-ts/utils/employee';

const subjectDid = 'did:web:api.acme.org:individual:shared-editor-001';

const bundle = new BundleEditor()
  .setBundleOperation(EmployeeBundleOperations.create)
  .setAllowedResourceType('AllergyIntolerance')
  .newEntry('allergy-001')
  .setClaim('AllergyIntolerance.identifier', 'urn:uuid:allergy-001')
  .setClaim('AllergyIntolerance.subject', subjectDid)
  .setClaim('Composition.section', 'LOINC|48765-2')
  .doneEntry()
  .newEntry('medication-001')
  .setClaim('MedicationStatement.identifier', 'urn:uuid:medication-001')
  .setClaim('MedicationStatement.subject', subjectDid)
  .setClaim('Composition.section', 'LOINC|10160-0')
  .doneEntry()
  .newEntry('condition-001')
  .setClaim('Condition.identifier', 'urn:uuid:condition-001')
  .setClaim('Condition.subject', subjectDid)
  .setClaim('Composition.section', 'LOINC|11450-4')
  .doneEntry()
  .build();

const reader = new BundleReader(bundle);
const totalEntries = reader.getTotalOperations();
const firstEntryClaims = (
  reader.getEntries()[0] as { resource?: { meta?: { claims?: Record<string, unknown> } } }
).resource?.meta?.claims;
```

Read that as:

- use `doneEntry()` to return from one entry to the bundle
- use `BundleReader.getEntries()[index]` when you want numbered access to the
  built bundle entries and their raw `resource.meta.claims`
- use `BundleReader.openEntry(index)` for per-entry bundle response metadata
  such as status/issues
- use `getClaim(...)` while you are still editing an active entry before
  calling `build()`

## Sections, Counts, And Filters

This is the second gap that often gets mixed together with the missing
`asAllergy()` / `asMedication...()` / `asCondition()` editors.

There are really three separate questions:

- which IPS/clinical sections exist and what canonical codes identify them
- how to count resources by section or by resource family
- how to filter by date, severity, status, or other resource-specific fields

### Canonical Clinical Section Codes

The canonical shared section constants currently come from
`gdc-common-utils-ts/src/constants/healthcare.ts`.

The most relevant ones for GW clinical bundle work are:

- `PatientSummaryDocument` -> `LOINC|60591-5`
- `AllergiesAndIntolerances` -> `LOINC|48765-2`
- `HistoryOfMedicationUse` -> `LOINC|10160-0`
- `ProblemList` -> `LOINC|11450-4`
- `Results` -> `LOINC|30954-2`
- `Procedures` -> `LOINC|47519-4`
- `Immunizations` -> `LOINC|11369-6`
- `VitalSigns` -> `LOINC|8716-3`

GW individual clinical aliases map those sections like this:

- `IndividualClinicalSections.AllergiesAndIntolerances`
- `IndividualClinicalSections.Medications`
- `IndividualClinicalSections.Conditions`
- `IndividualClinicalSections.VitalSigns`

### What Exists Today

Today there is already useful but partial support upstream.

In `gdc-sdk-core-ts`, the document facade can:

- list sections with `getSections()`
- return resources that belong to one section with
  `getSectionResources(sectionCode, resourceType?)`
- return all resources of one type with `getResources(resourceType?)`
- filter one resource family by date with `getByDates(resourceType, start, end)`
- search text/display with `getContainingTextOrDisplay(resourceType, searchText)`

In `gdc-sdk-node-ts`, the current workspace response processor can:

- count total sections
- count total resources
- count resources per section in `totalResourcesInSection`
- return expanded resource views for custom app-side filtering

That means:

- section discovery exists
- section-level resource extraction exists
- date filtering exists, but only by resource family, not section + family + semantic field
- menu-style summary counts per section exist

### What Still Does Not Exist As One High-Level Helper

What is still missing is the next layer up, for example:

- "how many `AllergyIntolerance` rows are in `LOINC|48765-2`?"
- "give me `Condition` rows in `LOINC|11450-4` between two dates"
- "give me `MedicationStatement` rows in medication history ordered by clinical date"
- "filter allergies by `criticality` or `clinical-status`"
- "filter conditions by clinical/verification status"
- "return one DTO already shaped for menu/web/app rendering"

That gap is already tracked upstream in `gdc-sdk-node-ts/TODO.md`.

The concrete TODOs are:

- `query/filter consolidated resources by section`
- `query/filter consolidated resources by clinical date/date range`
- `add one high-level bundle summary helper suitable for assisted-channel/web/app menus`
  with counts for `medication`, `condition`, `allergy`, `note`, and
  `narrative/XHTML`
- `add one 101 path` that can `read section summaries`

### Resource-Specific Filter Inputs Already Have Shared Claim Vocabulary

Even though the high-level filter helper is still missing, the claim vocabularies
 already exist in `gdc-common-utils-ts`, which means the missing piece is mostly
 orchestration/view/helper surface, not raw semantics.

Examples:

- `AllergyIntolerance.criticality`
- `AllergyIntolerance.clinical-status`
- `AllergyIntolerance.verification-status`
- `AllergyIntolerance.onset-datetime`
- `Condition.clinical-status`
- `Condition.verification-status`
- `MedicationStatement.effective`

So the likely correct future design is:

- `common-utils` keeps the canonical section constants and claim names
- `sdk-core` keeps document/bundle facades that can traverse one attached
  clinical bundle
- `sdk-node` exposes the higher-level
  `section summary + query/filter by family/date/semantic field` helpers for
  BFF/backend/app callers

### Current Practical Rule

If you need this today:

- use shared section constants from `HealthcareCoreSections` /
  `HealthcareBasicSections`
- use `createFhirDocumentFacade(...).getSections()` to discover sections
- use `createFhirDocumentFacade(...).getSectionResources(section, type)` to
  count resources by section and family
- use `getByDates(type, start, end)` for basic date filtering
- use expanded `views` from `sdk-node` when you need temporary app-side custom
  filtering

If you need a polished high-level API like:

- `getSectionSummary(...)`
- `getAllergies({ section, criticality, start, end })`
- `getConditions({ section, clinicalStatus, start, end })`
- `getMedications({ section, start, end })`

that is still upstream TODO territory, mainly in `gdc-sdk-node-ts`.

## Proposed Shared Query And Narrative Contract

This is the practical contract that would make the section/filter/narrative
story coherent across `common-utils`, `sdk-core`, `sdk-node`, and consumers
such as chat/voice apps.

### Section Selector Rule

Use `sections?: readonly string[]` everywhere instead of one single
`section?: string`.

Rule:

- `sections === undefined` means all sections
- `sections.length === 0` means all sections
- otherwise only the listed sections are included

That rule should be identical in:

- generic resource queries
- date queries
- per-family clinical queries
- section summaries

### Proposed Generic Types

```ts
type ClinicalSectionsSelector = readonly string[] | undefined;

type ClinicalResourceQuery = Readonly<{
  sections?: readonly string[];
  resourceType?: string;
  start?: string;
  end?: string;
  searchText?: string;
}>;

type LocalTextAndIntDisplay = Readonly<{
  localText?: string;
  internationalDisplay?: string;
  combined?: string;
}>;

type NarrativeResult = Readonly<{
  xhtml?: string;
  source: 'resource.text.div' | 'derived-from-claims' | 'missing';
}>;

type ClinicalSectionSummary = Readonly<{
  sectionsRequested: readonly string[];
  sectionsResolved: readonly string[];
  totalResources: number;
  totalNarratives: number;
  totalNotes: number;
  countsBySection: Readonly<Record<string, number>>;
  countsByResourceType: Readonly<Record<string, number>>;
  countsBySectionAndResourceType: Readonly<Record<string, Readonly<Record<string, number>>>>;
}>;
```

### Proposed Generic Methods

```ts
getResources(query?: ClinicalResourceQuery): FhirResourceLike[];

getSectionSummary(input?: {
  sections?: readonly string[];
}): ClinicalSectionSummary;

getLocalTextAndIntDisplay(resource: FhirResourceLike): LocalTextAndIntDisplay;

getXhtmlOrDerived(resource: FhirResourceLike): string | undefined;

getNarrative(resource: FhirResourceLike): NarrativeResult;
```

Recommended behavior:

- `getResources({ sections })` filters by section first
- then optionally by `resourceType`
- then by date range when `start` or `end` is present
- then by `searchText` when present

### Proposed Family-Specific Methods

Keep semantic filters out of the generic query and move them to the
resource-family helpers.

```ts
getAllergies(input?: {
  sections?: readonly string[];
  start?: string;
  end?: string;
  clinicalStatus?: readonly string[];
  verificationStatus?: readonly string[];
  criticality?: readonly string[];
  category?: readonly string[];
}): FhirResourceLike[];

getConditions(input?: {
  sections?: readonly string[];
  start?: string;
  end?: string;
  clinicalStatus?: readonly string[];
  verificationStatus?: readonly string[];
  category?: readonly string[];
}): FhirResourceLike[];

getMedications(input?: {
  sections?: readonly string[];
  start?: string;
  end?: string;
  status?: readonly string[];
  searchText?: string;
}): FhirResourceLike[];

getVitalSigns(input?: {
  sections?: readonly string[];
  start?: string;
  end?: string;
  code?: readonly string[];
}): FhirResourceLike[];
```

### Local Text And International Display

`getLocalTextAndIntDisplay(resource)` should exist because the same resource can
carry:

- one local or user-facing text
- one canonical/international coded display

Suggested formatting rule for the `combined` field:

- only `localText` -> return local text
- only `internationalDisplay` -> return international display
- both exist and differ -> `localText + " (" + internationalDisplay + ")"`
- both exist and are equal -> return only one of them

Examples:

- `Tension arterial`
- `Blood pressure`
- `Tension arterial (Blood pressure)`

### XHTML / Narrative Derivation

`getXhtmlOrDerived(resource)` should follow this order:

1. if `resource.text.div` exists, return it unchanged
2. otherwise derive XHTML from canonical `meta.claims`
3. if there is not enough information, return `undefined`

The derived XHTML should be simple and deterministic.

Suggested structure:

- first line: main label from `getLocalTextAndIntDisplay(resource).combined`
- second line: clinical date if present
- third line: period start if present
- fourth line: period end if present and period start exists
- then resource-family-specific lines

Important date/period rules:

- if one canonical date exists, render one dedicated line
- if `period start` exists, render one dedicated line for it
- if `period end` exists and `period start` also exists, render one dedicated
  line for end
- if `period start` exists and `period end` is empty, still render the start
  line and omit the end value

Suggested rendering shape:

```html
<div>
  <p>Main label</p>
  <p>Date: 2026-06-20</p>
  <p>Start: 2026-06-01</p>
  <p>End: 2026-06-15</p>
</div>
```

### Claim Sources For Derived XHTML

The derivation should not depend only on one generic `code-text`.

The resolver should check canonical family-specific claims such as:

- generic code text / local text
- medication text
- vaccine code text
- observation code text
- condition code text
- allergy code text

That allows XHTML to be derived even when the resource has only `meta.claims`
and no pre-rendered `text.div`.

### Family-Specific Narrative Rules

The generic lines above are not enough. After them, add deterministic
family-specific lines.

#### AllergyIntolerance

When present, render lines for:

- `clinical-status`
- `verification-status`
- `criticality`
- category
- onset date/time

#### Condition

When present, render lines for:

- `clinical-status`
- `verification-status`
- category
- onset/date if present

#### MedicationStatement

When present, render lines for:

- medication text
- status
- effective date
- dose quantity value + unit
- timing frequency / period / period unit
- note

#### Immunization

When present, render lines for:

- vaccine text or vaccine code display
- status
- occurrence date
- performer or note when available

#### Vital Signs / Observation

For vital signs, the XHTML should be more specific than the generic resource
line.

Always try to render:

- the vital-sign type label
- quantity value
- quantity unit

For blood pressure specifically:

- systolic and diastolic should be treated as the expected pair
- render both when available
- if only one exists, render the available one without inventing the other

Suggested blood-pressure XHTML:

```html
<div>
  <p>Blood pressure</p>
  <p>Date: 2026-06-20T10:00:00Z</p>
  <p>Systolic: 120 mmHg</p>
  <p>Diastolic: 80 mmHg</p>
</div>
```

For other vital signs:

- heart rate -> value + `beats/min`
- body temperature -> value + `Cel`
- other Observation-based vital signs -> code label + quantity value + unit

### Repo Ownership Of This Contract

Recommended ownership split:

- `gdc-common-utils-ts`
  - canonical section constants
  - claim names
  - text/narrative derivation helpers
  - shared DTO types
- `gdc-sdk-core-ts`
  - bundle/document traversal
  - generic `getResources(...)`
  - generic `getSectionSummary(...)`
- `gdc-sdk-node-ts`
  - high-level family-specific filters and app/BFF-friendly summaries
- `uhc-unid-chat-node`
  - consumes those helpers and does not rebuild narrative/filter logic locally

# High-Level Tutorial Boundaries

> 101 note
> - Teach here: the GW-local rule for what a `101` may claim to teach.
> - Do not present GW as the first login/profile/runtime entrypoint for self-managed users; that starts upstream in `sdk-front` or `sdk-node`.
> - Read [101-README.md](./101-README.md) for the ordered path and upstream runtime entrypoints.

Status: Canonical

This note exists to stop one recurring mistake:

- calling low-level transport/plumbing tests "`101`"
- using internal claims-only builders as if they were the intended newbie API
- mixing GW submit contracts with real DIDComm pack/unpack examples

Canonical user-story boundary:

- first story step for self-managed users:
  `login -> loadProfile -> actor facade`
- that step is owned by `gdc-sdk-front-ts` or `gdc-sdk-node-ts`
- GW owns the backend route/contract/policy/indexing side after that point

Canonical individual document story:

- teach `Bundle.type=document` first
- the first bundle entry should be `Composition`
- `Communication` comes next as the transport/read wrapper
- frontend/BFF read paths should read `DIDComm/plain -> Communication -> attached document bundle`
- backend search should be taught separately with FHIR params such as `Composition.section`
- raw internal plumbing stays secondary

## Rule For `101`

A doc or test may be called `101`, "newbie", "didactic", or "high-level" only
when it teaches the public mental model first.

That means it should primarily show:

- typed drafts, editors, facades, or SDK methods
- business intent such as create/search/update/purge/grant/request
- the minimum object graph the integrator is expected to know
- the canonical request/response contract actually exposed to callers

It must not primarily teach:

- raw `meta.claims` authoring when a public setter/helper exists
- `upsert...` plumbing intended for internal composition
- wallet `pack/unpack` details when the target reader is an app integrator
- GW internal queue/poll plumbing unless the tutorial is specifically about runtime transport

## Allowed `101` Escape Hatch

Low-level details may appear in a `101` only as a clearly marked escape hatch:

- "fallback"
- "internal plumbing"
- "advanced transport note"
- "when typed helper does not exist yet"

Those sections must stay secondary. They cannot be the main narrative.

## Test Naming Rule

Use names that match the abstraction level:

- `101-*`: public high-level usage
- `*-api.test.ts`: route/contract behavior
- `*-integration.test.ts`: end-to-end GW behavior
- `*-transport*` or `*-wallet*`: DIDComm/wallet mechanics
- `*-claims*` or `*-fixtures*`: low-level payload rendering

Avoid misleading names such as:

- builders with `Didcomm` in the name when they only render `thid + body`
- "`101`" tests that require understanding raw claims vocabulary first

## GW Local Boundary

In this repo, the local demo submit shape:

- `thid`
- `body`
- `body.resourceType = Bundle`
- `body.entry[0].resource = Communication`

is the GW async submit contract.

It is not, by itself, a full DIDComm plaintext message.
It is also not the main teaching model for individual document cases; that
story starts with the document bundle and the `Composition` entry first.

## Current Teaching Split

Use this split consistently in docs and test comments:

- `gdc-sdk-core-ts`: high-level business drafts/editors/readers
- `gdc-common-utils-ts`: `Bundle -> Communication -> DIDComm` wrapping and wallet transport
- `gdc-sdk-node-ts`: runtime submit/poll orchestration against GW
- `gwtemplate-node-ts`: backend contract, policy, indexing, and route behavior

## Method Matrix Requirement

When documenting one resource family, prefer one small matrix with these columns:

- data family
- high-level create/edit API
- high-level read/search API
- submit endpoint
- poll endpoint
- fallback/escape hatch if typed helper does not exist

If that matrix does not exist yet, do not fill the gap by promoting plumbing as
the main tutorial.

## Immediate Correction Rule

When a current example is technically useful but too low-level for `101`:

1. keep the executable test if it proves behavior
2. rename it or describe it as `transport`, `fixture`, `claims`, or `plumbing`
3. add one short bridge note pointing to the true high-level entrypoint

That is the minimum fix expected before adding more docs.

# Organization Test Network credential audit

## Runtime policy

Host `Organization/_transaction` has two explicit verification sources:

- no Test Network admission VC: forward the legal evidence to ICA;
- attached `OrganizationTestNetworkCredential`: require exactly three signed
  domain VCs marked `TestNetworkCredential` and accept only
  when both the authoritative host route and `NETWORK_MODE` are exactly
  `test-network`. `resource.verification.resourceType` remains `contract` and
  is never a client-controlled environment selector.

The Test Network verifier requires `HOST_ORGANIZATION_AUTHORIZATION_ISSUERS`
to contain the exact VC issuer DID. Canonically it resolves issuer and signer
did:web documents and checks the current controller/assertion relationships.
Until an employee governance key is published, the explicitly configured
`HOST_ORGANIZATION_AUTHORIZATION_SIGNERS` registry may bind that issuer to one
exact employee DID containing its stable email-hash member id, `RESPRSN` role,
active/revoked status and RFC 9278 ML-DSA-65 key thumbprint. During first key
publication it may explicitly allow the shared portal/host attestation, which
is emitted only after the BFF unlocks the existing reviewer wallet. An embedded
JWK is never trusted without a registered thumbprint or valid attestation.
Fabric may replace this configuration as the authoritative policy registry. It then
verifies all detached ML-DSA-65 proofs and exact PDF digest, organization
DID/identifier, distinct representative/controller emails, RFC 9278 public-key
commitment and delivered postal licence.

Failure of any check is a security error. The host never falls back from a bad
attached VC to ICA and never accepts the Test Network VC for another resource
type. The response records a proof summary in `verificationResponse` and the
three domain VCs in `vc[]`; ICA responses retain `icaResponse`.

## Boundaries

This transaction creates the pending tenant registration and Offer and stores
the verified postal-code binding as server-owned pending metadata. It does not
prove Order acceptance, redeem the code, complete DCR, activate the tenant or
change Fabric membership. Order requires the same clear code, recomputes the
salted scrypt binding with `HOST_POSTAL_ACTIVATION_PEPPER`, and assigns that
exact value to the controller licence. A second generated code is forbidden.
Only exchange plus DCR may complete activation.

Production remains ICA-backed. Qualified-signature and certificate policy must
not be inferred from the Test Network ML-DSA proof.

# Test-Local Topology And Fabric Env Loader

## Purpose

This note fixes the local/demo model so it stops being confused with the shared
Fabric test network.

Use this document when:

- a local Docker setup must be shown to an auditor, evaluator, or integrator
- a host must start locally with Fabric credentials
- `test-local`, `test-network`, and `network` need to be kept separate

## Environment naming

Use these physical artifact roots:

- `fabric-multicloud/artifacts/test-local/`
- `fabric-multicloud/artifacts/test-network/`
- `fabric-multicloud/artifacts/network/`

Do not treat `test` as the final canonical environment name anymore when the
intent is a real Fabric-backed network.

Meaning:

- `test-local`
  - minimal local Docker deployment
  - reproducible demo environment
  - useful for audits and integrations
- `test-network`
  - shared non-production Fabric deployment
  - current GKE / multicloud validation environment
- `network`
  - production environment

## Local topology

For the minimal local demonstration, keep the roles separate:

- `Acme CA`
  - runs the local `gdc-ca`
  - trust-anchor / CA side of the local environment
- `Acme ICA`
  - runs the local `gdc-ica`
  - validates onboarding and emits VC/trust artifacts
- `Acme Host`
  - runs the host/gateway service
  - is the operational Fabric client
- `Acme Tenant`
  - is the hosted organization
  - is not the same thing as the host

Important:

- `health-care` is not a fourth technical organization
- `health-care` is the tenant sector / functional domain
- the host may specialize in `health-care`, but that does not make
  `health-care` its own CA/ICA/Host organization

## Minimal local containers

The smallest useful local stack is:

- `gdc-ca`
- `gdc-ica`
- `orderer`
- `peer0`
- `acme-host`
- optional `couchdb`

This is enough to demonstrate:

- trust bootstrap
- host onboarding
- host Fabric credential loading
- ledger submission path

## Artifact layout

The host loader expects a standard structure like:

```text
fabric-multicloud/artifacts/<environment>/pki-host/<MSP_ID>/
  admin/msp/signcerts/cert.pem
  admin/msp/keystore/*_sk
  .../tlscacerts/*
```

Examples:

```text
fabric-multicloud/artifacts/test-local/pki-host/ACMEHOSTMSP/...
fabric-multicloud/artifacts/test-network/pki-host/UNIDMSP/...
fabric-multicloud/artifacts/network/pki-host/CONNECTHEALTHMSP/...
```

## Host startup helper

The helper script is:

- [load-fabric-host-env.sh](https://github.com/Global-DataCare/gwtemplate-node-ts/blob/main/scripts/load-fabric-host-env.sh)

Usage:

```bash
cd $HOME/GITS/gdc-workspace/gwtemplate-node-ts
source ./scripts/load-fabric-host-env.sh UNIDMSP
npm run api:local-demo
```

It exports:

- `LEDGER_PROVIDER_DEFAULT=fabric`
- `LEDGER_PROVIDER_MAP=network=fabric`
- `LEDGER_MSP_ID=<MSP_ID>`
- `LEDGER_FABRIC_MSP_ID=<MSP_ID>`
- `LEDGER_FABRIC_ITEM_TYPE=credential`
- `HLF_CONNECTION_PEER`
- `HLF_CONNECTION_PEM`
- `HLF_CERTIFICATE`
- `HLF_PRIVATE_KEY`

The process owns one Fabric identity and one peer connection. Older
`HLF_*_<MSP_ID>` names remain accepted only as a compatibility fallback.

Current default:

- peer endpoint: `peer0:7051`

This default is valid only when:

- the host runs next to its local peer
- the peer service name is `peer0`
- the port is `7051`

## Kubernetes and public peer endpoints

`peer0:7051` is Kubernetes-local naming. It resolves directly only when the GW
can use the peer's cluster DNS, normally because both workloads are in the same
cluster or share an explicitly configured private network and DNS zone.

When an organization owns its peer in another cluster or GCP project:

- expose the peer through a reserved static address or private cross-project
  endpoint
- configure `HLF_CONNECTION_PEER` with that endpoint
- keep the GW HTTP address and the Fabric peer address as separate resources
- allow the GW's real egress range on TCP 7051

A static GW address and a static peer address do not replace one another. GKE
node egress addresses and source-range allowlists can still change when a node
pool is recreated, so either reconcile that allowlist automatically or prefer
private connectivity. Do not rely on a manually added `hostAliases` entry as
the durable source of peer discovery.

## Current limitation

Today the helper resolves from:

- `fabric-multicloud/artifacts/test/pki-host`

That is only a backward-compatible temporary root.

The target convention should be:

- `test-local`
- `test-network`
- `network`

## Practical rule

For local demo work:

- use `NETWORK_MODE=test-local` only if the runtime explicitly supports it
- otherwise keep the logical mode aligned with current code expectations and
  only move the physical artifact layout first

For the current `gwtemplate` runtime:

- `test`
- `test-network`
- `network`

are logical network selectors

and:

- provider routing is selected by `LEDGER_PROVIDER_MAP`
- certificate paths are still supplied externally by the loader script

So:

- network mode does not automatically derive certificate paths
- the loader script still provides the `HLF_*` material explicitly

## One-command local bootstrap

For a "do not make me think" local Docker bootstrap, use:

- [bootstrap-test-local-fabric.sh](https://github.com/Global-DataCare/gwtemplate-node-ts/blob/main/scripts/bootstrap-test-local-fabric.sh)

This script:

1. bootstraps the local Fabric Docker devnet
2. generates the Fabric backend env
3. merges it into `.env.local-fabric`

Usage:

```bash
cd $HOME/GITS/gdc-workspace/gwtemplate-node-ts
bash ./scripts/bootstrap-test-local-fabric.sh
npm run api:local-fabric
```

Requirements:

- Docker running
- `.env.local-demo` already created

This is the intended `test-local` operator path for:

- auditors
- evaluators
- junior integrators

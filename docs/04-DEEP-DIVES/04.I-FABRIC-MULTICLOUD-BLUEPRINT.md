## Why this moved

`gwtemplate-node-ts` consumes Fabric. It is not the owner of:

- `fabric-ca-root` / `fabric-ca-ica`
- configtx/channel bootstrap
- Kubernetes manifests for Fabric
- local Fabric devnet lifecycle
- multi-ICA PKI layout

Those assets now live in `fabric-multicloud/` beside this repo.

## What remains relevant from GW

GW still owns:

- Fabric gateway client usage
- connection profile consumption
- runtime identities provided through env vars
- application logic and tests that exercise the ledger

`fabric-multicloud/devnet/fabric-v3/external-chaincodes` is the canonical
source for shared identity chaincodes. The `organization-sc` and
`cryptographickey-sc` directories under `gwtemplate-node-ts/chaincode` are a
temporary packaging mirror used by the documented local-network bootstrap;
they are not a second contract authority and do not exist merely to publish
the source. Any behavior change must be authored and released from the
canonical Fabric repository, synchronized into the mirror, and verified with:

```bash
npm run check:identity-chaincode-parity
```

The full Docker smoke runs this guard before it resets or deploys the local
devnet. A mismatch is therefore a release failure, preventing local tests from
silently exercising different transactions than the CCAAS images deployed to
Kubernetes.

The recommended local dev path is:

1. bootstrap Fabric in `../fabric-multicloud/devnet/fabric-v3`
2. generate `.env.fabric-devnet`
3. run GW tests or local backend using that env file

Organization registration retries use the detached JWS as the authentication
boundary. After a partial Fabric commit, a reissued VC is the same legal
organization only when canonical issuer, type/schema, `credentialSubject` and
evidence are unchanged. VC ids, validity timestamps, status references and
proof envelopes are issuance metadata; changing the signed identity remains a
409 conflict.

## Temporary compatibility layer

Some PKI helper entrypoints still live in this repo because the current GW
runtime and demo bootstrap paths still import them directly:

- `scripts/generate-root-ca.ts`
- `scripts/generate-ica.ts`
- `scripts/generate-pki-chain.ts`
- `src/utils/pki-chain.ts`

They already write CA state into the sibling `../fabric-multicloud` folder and
should be treated as compatibility shims, not as long-term ownership of Fabric
infrastructure by `gwtemplate-node-ts`.

domain repos, not here.

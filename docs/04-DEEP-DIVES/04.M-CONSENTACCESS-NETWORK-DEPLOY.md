# ConsentAccess On UNID Test-Network

This note fixes the exact deployment path for `consentaccess-sc` on the real Kubernetes-backed `test-network`.

## Why This Exists

The local devnet path already proves that:

- the chaincode package is valid
- the consent access write-path in `GW CORE` works
- `ConsentManager` can call `registerConsentAccessBundle(...)`

The UNID test-network path adds the real shared-network steps:

- build and push a CCAAS image for GKE
- deploy the external chaincode service in-cluster
- install, approve and commit the chaincode on `health-care-eu`

## Canonical Command

Run:

```bash
cd $HOME/GITS/gdc-workspace
bash ./gwtemplate-node-ts/chaincode/scripts/deploy-consentaccess-unid-test-network.sh
```

Or from the package script:

```bash
cd $HOME/GITS/gdc-workspace/gwtemplate-node-ts
npm run chaincode:deploy:test-network-unid
```

## What The Script Assumes

- active `gcloud` auth
- active kube context for `UNID`
- existing Fabric namespace `test-fabric-v3`
- existing channel `health-care-eu`
- existing Kubernetes secrets:
  - `peer-msp`
  - `osnadmin-tls`
- current peer service name:
  - `peer0`
- current orderer service name:
  - `orderer`

## What The Script Does

1. runs `consentaccess-sc` unit tests
2. generates `metadata.json`
3. builds the CCAAS archive with `connection.json` pointing to
   `consentaccess-sc:9999`
4. calculates the Fabric `PACKAGE_ID` locally before install
5. builds and pushes the external chaincode image to Artifact Registry
6. applies a Kubernetes `Deployment` and `Service` for `consentaccess-sc`
7. applies a Kubernetes `ConfigMap` containing `consentaccess-sc-caas.tgz`
8. recreates a lifecycle `Job`
9. the job installs, approves and commits the chaincode on `health-care-eu`

## Step By Step Debug Sequence Used

This is the exact order used while debugging the real UNID deployment:

1. validate the chaincode package locally
   - `npm test`
   - `npm run metadata`
2. generate the CCAAS archive
3. calculate the `PACKAGE_ID` locally
4. create the Artifact Registry repository if missing
5. build and push the external chaincode image
6. apply the CCAAS `Deployment` and `Service`
7. publish a normalized admin/org MSP secret for the lifecycle job
8. run the lifecycle job:
   - `install`
   - `approveformyorg`
   - `commit`
9. if lifecycle fails, inspect:
   - job logs
   - runtime pod logs
   - peer joined channels
   - orderer `osnadmin channel list`

## Current Blocker

Two kinds of blockers were encountered.

### 1. Tooling/auth blockers

If `kubectl` or `gcloud` fails with:

- `Reauthentication failed`
- `cannot prompt during non-interactive execution`

then the script itself is still correct, but the shell session must refresh GCP
auth before the deploy can run end-to-end.

### 2. Deployment/runtime blockers already seen

These were all observed during the real UNID run:

- `FABRIC_CFG_PATH ... does not exist`
  - fix: resolve `config/` relative to the actual pinned Fabric binary path
- malformed Kubernetes YAML from unquoted values
  - fix: quote every env value that can contain `:` or `'`
- `CHAINCODE_ID` polluted by log text
  - fix: print the info banner to `stderr`, not `stdout`
- CCAAS runtime tried to bind to `consentaccess-sc:9999`
  - fix: separate:
    - advertised address for Fabric package: `consentaccess-sc:9999`
    - runtime listen address in pod: `0.0.0.0:9999`
- lifecycle job used non-admin MSP
  - fix: mount normalized org/admin MSP, not peer runtime MSP
- lifecycle job read macOS AppleDouble files like `._cert.pem`
  - fix: package tarballs with:
    - `COPYFILE_DISABLE=1`
    - `--exclude='._*'`
    - `--exclude='__MACOSX'`
- lifecycle job failed with:
  - `channel does not exist`
  - fix still pending at network level: rejoin or recreate the orderer channel

## Can One Docker Image Be Reused Across Orgs Or Networks?

Yes, usually.

If the chaincode source is the same:

- the same Docker image can be reused across:
  - organizations
  - clusters
  - test/prod-like networks

What changes per network is not usually the image itself, but:

- the Fabric lifecycle on each channel
  - `install`
  - `approveformyorg`
  - `commit`
- the CCAAS package metadata
  - especially the advertised chaincode address in `connection.json`
- the runtime Kubernetes `Deployment`/`Service`
- the policies and channel membership

Practical rule:

- same code -> same image can be reused
- different network/channel/org -> lifecycle still has to be run there

So, yes:

- you can build the chaincode image once locally
- push it once
- and reuse that image in Kubernetes for multiple organizations or networks

But you still need separate Fabric lifecycle steps for each target channel and
each organization that must approve it.

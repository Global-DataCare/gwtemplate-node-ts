# 04.M Local And Fabric Environment Profiles

## Purpose

This note fixes one recurring source of confusion in local development:

- `local-demo`
- `local-fabric`
- `dev-fabric`

These names describe different runtime targets and they must not be mixed.

## Canonical Profiles

### 1. `.env.local-demo`

Use this profile when GW CORE runs fully local with in-memory adapters.

Properties:

- API runs on the local machine
- storage can stay in memory
- ledger writes stay in memory
- `NETWORK_MODE=test`

This is the fastest profile for everyday API work when Fabric is not needed.

Typical command:

```bash
npm run api:local-demo
```

### 2. `.env.local-fabric`

Use this profile when GW CORE runs locally but must talk to the Docker-based
Fabric local network.

Properties:

- API runs on the local machine
- blockchain writes go to local Fabric in Docker
- `NETWORK_MODE=local-network`
- host jurisdiction is `EU`
- tenant demo jurisdiction can still be `ES`

This is the canonical profile for local consent-access blockchain testing.

Local channel naming in this profile:

- healthcare writes: `health-care-local`
- identity ledger reads/writes: `identity-local`

Typical commands:

```bash
npm run prepare:local-fabric-env
npm run api:local-fabric
```

### 3. `.env.local-fabric-devnet`

This file is now only a compatibility alias.

Rules:

- keep it generated so old scripts and local habits do not break
- do not use it as the primary documented name anymore
- primary name is `.env.local-fabric`

### 4. `dev-fabric` concept

`dev-fabric` is a useful name for a future or external profile, but it should
mean something different from `local-fabric`.

Recommended meaning:

- GW CORE does not talk to Docker Fabric on the same machine
- GW CORE targets a remote/shared Fabric environment
- typical network mode there would be `test-network`

So:

- `local-fabric` = local machine + local Docker Fabric
- `dev-fabric` = local or remote GW CORE + remote shared Fabric dev/staging

## Network Mode Mapping

The intent should be:

- `local-demo` -> `NETWORK_MODE=test`
- `local-fabric` -> `NETWORK_MODE=local-network`
- `dev-fabric` -> `NETWORK_MODE=test-network`

## Jurisdiction Mapping

For the local Fabric topology used in this repository:

- host routes use `cds-eu`
- tenant demo routes can use `cds-es`

That means:

- host onboarding:
  - `/host/cds-eu/v1/local-network/...`
- tenant business resources:
  - `/<tenantId>/cds-ES/v1/health-care/...`

Those two values are intentionally different and must not be collapsed into one
variable.

## Current Commands

Preferred local Fabric commands:

```bash
npm run prepare:local-fabric-env
npm run api:local-fabric
bash ./scripts/bootstrap-single-tenant.sh
bash ./scripts/demo-create-individual-organization.sh
bash ./scripts/demo-communication-medications-ips.sh
bash ./scripts/smoke-consentaccess-local-network.sh
```

Notes:

- `demo-create-individual-organization.sh` is the reusable baseline bootstrap
  for the legacy-compatible individual onboarding flow.
- It uses the canonical route
  `/{tenantId}/cds-{jurisdiction}/v1/{sector}/individual/org.schema/Organization/_batch`.
- The older `individual/org.schema/Person` route remains only as a legacy
  compatibility alias and should not be used for new local demos.
- `demo-communication-medications-ips.sh` now creates that individual by
  default and accepts `--no-create-individual` for negative-path tests.
- `smoke-consentaccess-lifecycle-local-network.sh` measures the lifecycle of
  one atomic consent rule in local Fabric:
  - activate
  - revoke
  - reactivate
  - and prints per-operation timings in milliseconds
- the local Fabric naming intentionally differs from `test-network`:
  - `local-network` uses `health-care-local` and `identity-local`
  - `test-network` keeps regional channels such as `health-care-eu`

## Compatibility Notes

These aliases still exist:

- `api:local-fabric-devnet` -> delegates to `api:local-fabric`
- `.env.local-fabric-devnet` -> generated as a copy of `.env.local-fabric`

They should remain for compatibility, but new documentation should prefer the
canonical `local-fabric` names.

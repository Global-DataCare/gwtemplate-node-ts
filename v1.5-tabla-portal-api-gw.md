histórica estable y completando las operaciones de organización que un BFF del

## Organizaciones

| Portal API | Método | Para qué lo usa el frontend | Qué hace el backend del portal por detrás | Estado GW/OpenAPI |
|---|---|---|---|---|
| `/organization-registrations` | `POST` | iniciar el alta legal de una organización/tenant en el host elegido | llama a `POST /host/cds-{jurisdiction}/v1/{sector}/registry/org.schema/Organization/_transaction`; después puede continuar internamente con `_activate` y `Order/_batch` si el flow backend lo requiere | publicado |
| `/organization-registrations/{requestId}` | `GET` | ver estado o resultado del proceso de alta | lee el estado guardado por el portal o reproyecta el resultado de `_transaction-response`; si el backend encadena más pasos internos, expone aquí el estado agregado del proceso | publicado |
| `/organizations/{organizationId}/did-binding` | `POST` | reemplazar los aliases públicos `alsoKnownAs` del DID document efectivo de la organización | conceptualmente llama a `Organization/_binding`; por ahora el BFF solo puede tratarlo como capability pendiente o helper interno, porque GW CORE aún no publica esta route ni en runtime ni en OpenAPI | pendiente |
| `/organizations/{organizationId}/did-binding` | `GET` | leer el binding DID público actual de la organización | conceptualmente devuelve el DID document actual y su lista `alsoKnownAs`; hoy requiere lectura/resolución desde la proyección DID actual, no una route pública dedicada en GW | pendiente |
| `/organizations/{organizationId}/deactivate` | `POST` | desactivar operativamente una organización/proveedor | llama a la capability de tenant disable y bloquea la operación si siguen existiendo descendants activos | publicado |
| `/organizations/{organizationId}/purge` | `POST` | borrar de forma irreversible una organización/proveedor | llama a tenant purge solo si la organización ya está desactivada y sus descendants ya fueron purgados según política; por defecto salta `Communication` retenidas mientras `COMMUNICATION_RETENTION_DISABLED=false` | publicado |
| `/organizations/{organizationId}/license-offers` | `POST` | pedir una oferta para comprar/agregar licencias adicionales | hoy el portal tendría que orquestarlo como capability propia; en GW falta una route pública convergida para emitir esta offer de compra | pendiente |
| `/organizations/{organizationId}/license-offers` | `GET` | listar ofertas de licencias conocidas por el portal | usa historial comercial/materializado del portal | parcial |
| `/organizations/{organizationId}/license-offers/{offerId}` | `GET` | ver detalle de una oferta concreta de licencias | devuelve precio, cantidad, moneda y estado conocidos por el portal | parcial |
| `/organizations/{organizationId}/license-orders` | `POST` | solicitar compra/agregado de licencias adicionales para la organización | conceptualmente dispara un nuevo flow de offer -> order -> pago; hoy no hay route pública GW convergida para esto y el portal tendría que orquestarlo con su capa comercial/backend | pendiente |
| `/organizations/{organizationId}/license-orders` | `GET` | listar compras de licencias lanzadas desde el portal | usa historial comercial/materializado del portal | parcial |
| `/organizations/{organizationId}/license-orders/{orderId}` | `GET` | ver estado de una compra concreta de licencias | devuelve el estado materializado por el portal | parcial |
| `/organizations/{organizationId}/license-orders/{orderId}/payment-confirmation` | `POST` | confirmar/verificar el pago de una compra de licencias para que se emitan los seriales | hoy el portal tendría que cerrar este paso con su backend comercial y luego provocar en GW la creación interna de nuevas `device-licenses` | pendiente |
| `/organizations/{organizationId}/licenses` | `GET` | listar licencias/plazas visibles de la organización | debe exponerse como fachada real del portal sobre el pool `device-licenses`; hoy la fuente de datos existe y el runtime convergido ya la consume | publicado |
| `/organizations/{organizationId}/employees` | `POST` | crear empleados/profesionales | envía `Employee/_batch` a GW | publicado |
| `/organizations/{organizationId}/employees` | `GET` | listar empleados/profesionales visibles para el portal | usa almacenamiento del portal o lectura materializada | parcial |
| `/organizations/{organizationId}/employees/{employeeId}` | `GET` | ver detalle de un empleado/profesional | devuelve el detalle conocido por el portal | parcial |

## Resolución pública de DID web

Estas lecturas no sustituyen a los endpoints funcionales del portal para
organizaciones, employees, subjects o members. Son fachadas de resolución
pública del `did:web` efectivo que el portal presenta al navegador, pero cuyo
documento debe corresponder al actor real publicado en GW bajo el host o el
`tenantId` final.

| Portal API | Método | Para qué lo usa el frontend | Qué hace el backend del portal por detrás | Estado GW/OpenAPI |
|---|---|---|---|---|
| `/.well-known/did.json` | `GET` | resolver el DID público del portal/host expuesto al navegador | devuelve el DID document público del host o una proyección frontal equivalente, resolviendo contra el DID real alojado en GW | publicado |
| `/organizations/{organizationId}/.well-known/did.json` | `GET` | resolver el DID público de una organización/tenant ya registrada | resuelve o reproyecta el DID document efectivo del tenant publicado en GW bajo su `tenantId` real | parcial |
| `/organizations/{organizationId}/employees/{employeeId}/.well-known/did.json` | `GET` | resolver el DID público de un employee/profesional visible en el portal | devuelve una proyección pública del DID del employee cuando exista publicación/resolución soportada; el portal no debe inventar una identidad distinta de la alojada realmente en GW | parcial |
| `/subject/.well-known/did.json` | `GET` | resolver el DID público del subject/individual actual en experiencias portal centradas en la persona | resuelve o reproyecta el DID real del individual alojado en GW bajo el tenant y subject efectivos | parcial |
| `/subject/members/{memberId}/.well-known/did.json` | `GET` | resolver el DID público de un member invitado dentro del espacio individual/familiar | devuelve el DID document efectivo del member cuando la identidad ya esté materializada/publicada en GW | parcial |

## Regla de diseño para BFF vs frontend

- si la app usa `sdk-front` o un runtime confidencial equivalente, algunas de
  estas operaciones podrían hacerse sin BFF
- aun así, conviene mantener la tabla BFF porque:
  - el portal web sigue necesitando contratos funcionales estables
  - el BFF puede centralizar polling, auditoría, materialización y políticas
  - no todas las operaciones publicadas por el producto deben exponer
    directamente la complejidad submit/poll al navegador
- para onboarding legal de organización, la fachada pública propuesta para el
  frontend es `organization-registrations`
- en GW CORE, el paso canónico publicado para iniciar ese proceso sigue siendo
  `Organization/_transaction`
- pasos como `Organization/_activate` y `Order/_batch` pueden seguir
  ejecutándose dentro del backend/BFF sin formar parte del contrato público del
  frontend
- las lecturas `GET .../.well-known/did.json` del portal deben tratarse como
  fachadas de resolución pública del DID real alojado en GW, no como un
  espacio de identidad paralelo con documentos divergentes

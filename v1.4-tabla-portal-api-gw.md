## Organizaciones

| Portal API | Método | Para qué lo usa el frontend | Qué hace el backend del portal por detrás |
|---|---|---|---|
| `/organizations/{uuid}/activate-tenant` | `POST` | activar una organización legal en GW a partir de la prueba ICA / `vp_token` | llama a la activación host de GW y espera resultado |
| `/organizations/{uuid}/activate-tenant` | `GET` | ver estado o resultado de activación | lee estado guardado por el portal |
| `/organizations/{uuid}/deactivate` | `POST` | desactivar operativamente una organización/proveedor | llama a la capability de tenant disable y bloquea la operación si siguen existiendo descendants activos |
| `/organizations/{uuid}/purge` | `POST` | borrar de forma irreversible una organización/proveedor | llama a tenant purge solo si la organización ya está desactivada y sus descendants ya fueron purgados según política; por defecto salta `Communication` retenidas mientras `COMMUNICATION_RETENTION_DISABLED=false` |
| `/organizations/{uuid}/license-offers` | `POST` | pedir una oferta para comprar/agregar licencias adicionales | hoy el portal tendría que orquestarlo como capability propia; en GW falta una route pública convergida para emitir esta offer de compra |
| `/organizations/{uuid}/license-offers` | `GET` | listar ofertas de licencias conocidas por el portal | usa historial comercial/materializado del portal |
| `/organizations/{uuid}/license-offers/{offerId}` | `GET` | ver detalle de una oferta concreta de licencias | devuelve precio, cantidad, moneda y estado conocidos por el portal |
| `/organizations/{uuid}/license-orders` | `POST` | solicitar compra/agregado de licencias adicionales para la organización | conceptualmente dispara un nuevo flow de offer -> order -> pago; hoy no hay route pública GW convergida para esto y el portal tendría que orquestarlo con su capa comercial/backend |
| `/organizations/{uuid}/license-orders` | `GET` | listar compras de licencias lanzadas desde el portal | usa historial comercial/materializado del portal |
| `/organizations/{uuid}/license-orders/{orderId}` | `GET` | ver estado de una compra concreta de licencias | devuelve el estado materializado por el portal |
| `/organizations/{uuid}/license-orders/{orderId}/payment-confirmation` | `POST` | confirmar/verificar el pago de una compra de licencias para que se emitan los seriales | hoy el portal tendría que cerrar este paso con su backend comercial y luego provocar en GW la creación interna de nuevas `device-licenses` |
| `/organizations/{uuid}/licenses` | `GET` | listar licencias/plazas visibles de la organización | debe exponerse como fachada real del portal sobre el pool `device-licenses`; hoy no existe método convergido en SDK, pero la fuente de datos sí existe en GW |
| `/organizations/{uuid}/orders` | `POST` | confirmar la oferta/licencia de la organización legal | envía el order de organización a GW |
| `/organizations/{uuid}/orders` | `GET` | listar orders lanzadas desde el portal | lee historial guardado por el portal |
| `/organizations/{uuid}/orders/{orderId}` | `GET` | ver detalle de un order | devuelve el estado materializado en el portal |
| `/organizations/{uuid}/employees` | `POST` | crear empleados/profesionales | envía `Employee/_batch` a GW |
| `/organizations/{uuid}/employees` | `GET` | listar empleados/profesionales visibles para el portal | usa almacenamiento del portal o lectura materializada |
| `/organizations/{uuid}/employees/{employeeId}` | `GET` | ver detalle de un empleado/profesional | devuelve el detalle conocido por el portal |

## Host Lifecycle

Estas operaciones suelen ser administrativas y no se exponen al frontend
general, pero conviene dejar su contrato claro en la tabla del portal/backend.

| Portal API | Método | Para qué lo usa el frontend/backend | Qué hace el backend del portal por detrás |
|---|---|---|---|
| `/host/deactivate` | `POST` | desactivar operativamente el host/operador de alojamiento | llama a host disable y bloquea si todavía quedan hosted tenants registrados |
| `/host/purge` | `POST` | borrar de forma irreversible el host/operador | llama a host purge solo cuando no quedan tenants hospedados; para limpieza destructiva completa de tests puede requerir `COMMUNICATION_RETENTION_DISABLED=true` |

## Identidad Técnica Del Portal

Estas operaciones normalmente no las invoca el frontend de forma directa. Las gestiona internamente el backend del portal cuando hace falta.

| Operación interna | Para qué sirve |
|---|---|
| activation code exchange | canjear activation code por credencial inicial |
| device activation / DCR | registrar la clave pública/JWK del backend del portal como “device” técnico del actor |
| smart token | obtener token operacional con scopes para operaciones protegidas |

## Subject / Communications

Estas operaciones solo tienen sentido cuando el producto expone inbox,
historial, trazabilidad o depuración auditable de interacciones. No obligan al
frontend a conocer la complejidad interna del transporte `Communication`.

| Portal API | Método | Para qué lo usa el frontend | Qué hace el backend del portal por detrás |
|---|---|---|---|
| `/subject/communications` | `GET` | listar historial/canal de comunicaciones del subject | usa la fachada del portal sobre `individual/org.hl7.fhir.r4/Communication/_search` y devuelve resultados materializados/auditables |
| `/subject/communications/{communicationId}` | `GET` | ver el detalle de una comunicación concreta | devuelve el sobre auditado, sus adjuntos y/o referencias persistidas por GW |

## Subject / Communications Search Contract

La búsqueda real actualmente debe describirse como fachada de portal sobre el
surface de GW ya implementado, no como promesa genérica de cualquier ruta
FHIR/API.

| Aspecto | Contrato real a documentar en portal/backend |
|---|---|
| Recurso GW subyacente | `individual/org.hl7.fhir.r4/Communication/_search` |
| Forma recomendada de request al backend | `GET /subject/communications` con query params de portal, que el backend traduce a `Parameters` FHIR |
| Forma real de búsqueda en GW | `Parameters` o mapa plano equivalente |
| Filtros de participantes | `subject`, `actor`, `sender`, `recipient`, `user`, `target` |
| Claims searchParams soportados | `Communication.subject`, `Communication.sender`, `Communication.recipient`, `Communication.category`, `Communication.topic` |
| Rango temporal | `period-start`, `period-end` |
| Alias legacy aceptados | `sent-from`, `sent-to` |
| Paginación | `page`, `count` |
| Matching de participantes | normalizado para `did:`, `email:` / `mailto:`, `tel:` / `phone:` |
| Wildcards | se acepta `*` para búsquedas amplias sobre subject o participantes |
| Respuesta | `Bundle` tipo `search-response` con `total` y entradas `CommMsgExtended` / `Communication-search-response-v1.0` según proyección |
| Ordenación | resultados ordenados por `Communication.sent` |

## Lifecycle Summary

| Scope | Disable | Purge |
|---|---|---|
| Individual | reversible operational deactivation | irreversible deletion of registration, subject-scoped sections, and referenced blobs, skipping retained `Communication` by default |
| Tenant | stop being provider/published | only after descendant cleanup/purge, skipping retained `Communication` by default |
| Host | stop being discoverable as hosting operator | only after hosted tenant cleanup; full destructive cleanup may require `COMMUNICATION_RETENTION_DISABLED=true` in test/override environments |

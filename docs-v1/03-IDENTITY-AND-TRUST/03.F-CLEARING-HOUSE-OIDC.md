# Tenant Clearing House and Gaia-X verification

## Organizations and participants in data exchanges

The organization credential establishes the legal participant's identity.
Its ICA issuer signature is checked with the ICA's trusted public signing
keys, discoverable through its DID document and identity metadata. This is
separate from the identity and authority of the person or system performing
a data exchange. Requesters include professionals, the individual controller,
authorized family members and caregivers. The individual controller, the
organization controller and an employed professional retain distinct identities
and permissions. Organization accreditation alone does not grant record access.

In the professional flow, the requesting actor presents their own signed
evidence and uses their enrolled device key. Verification checks their current
organization relationship and the requested individual's consent and scope.
An authenticated organization system can also act under its own explicitly
authorized client identity; it does not become a professional or controller
merely by authenticating.

The EHR custodian's tenant Clearing House verifies operational access evidence.
The GXDCH standard-compliance integration validates participant and service
descriptions under the configured Gaia-X rules. These operations have distinct
inputs, authorization decisions and signed outputs.

## Professional access to an EHR

A professional selects an organization that provides an individual's data
index. A link in that index identifies data held by another organization, the
EHR custodian. The professional obtains a subject-scoped SMART token from the
index provider. The EHR asks its own tenant's Clearing House to verify that
token and the accompanying professional presentation before deciding access.

The gateway extension is:

```http
POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/identity/openid/smart/token/_verify
Content-Type: application/x-www-form-urlencoded
```

The EHR authenticates with `private_key_jwt` using its active DCR registration.
The assertion must target the exact endpoint and include bounded validity and
a unique `jti`. The gateway rejects replay, verifies the trusted index issuer's
signature, and asks the tenant-selected verifier for current credential and
consent checks. ES384 and the gateway's ML-DSA signatures are supported.

A successful response is a tenant-signed `token-introspection+jwt` containing
the original subject, purpose, scope and expiry. It also contains a fresh
tenant-signed presentation addressed to the EHR, retaining the original
credentials and binding the result to the original token and presentation
hashes. The outer signed response includes a fresh `jti` and a `nonce` equal
to the authenticated EHR assertion's `jti`, binding it to that request. A failed
evidence check returns signed `active: false`; invalid EHR
authentication is rejected before introspection.

## Personal access to an EHR

An individual controller or authorized family member uses their own registered
wallet key and canonical individual-member presentation. The index service
checks the current encrypted licence, exact individual, licensed relationship,
active device binding and requested data scope. The verified individual
controller has default access to that individual's data; family members and
caregivers receive only the scope permitted by current consent.

The index signs the SMART token. The EHR authenticates to its own tenant's
verification endpoint, which checks the original presentation and re-evaluates
current authority and consent. Revoked devices, inactive or expired licences,
withdrawn consent, another individual's data and scope expansion are denied.
An old signed token does not replace these current-state checks.

DCR registers a licensed family member without assigning controller or clinical
creator authority. The legacy controller request without a presentation still
requires current registered controller authority and cannot be used by a family
member; that legacy path does not produce the presentation evidence required
for federated verification.

## Current presentation checks

`ClearingHouseService` supports `local` and `remote` verification. The local
implementation verifies holder and issuer signatures and checks current
credential and key state. `test` can use real signatures with a memory ledger;
other networks use the configured Fabric provider for enrolled-requester
verification. Reported on-chain checks correspond to that provider's reads.

Remote trust is selected by the server from `CLEARING_HOUSE_TENANTS_JSON` for
the requesting tenant. It identifies the home tenant, an explicitly trusted
source tenant advertising `verifier`, its HTTPS endpoint, issuer, audience and
pinned public keys. A request cannot select its verifier or introduce a new
trusted key.

The corresponding backend endpoint is:

```http
POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/identity/openid/presentation/_verify
Authorization: Bearer <signed-backend-assertion>
Content-Type: application/json
```

`CLEARING_HOUSE_REQUESTERS_JSON` authorizes requester identities and pinned keys
per receiving tenant. Backend assertions bind the exact endpoint and canonical
SHA-256 request hash, expire within 120 seconds and cannot be replayed. A
successful signed receipt binds the VP hash, assurance level, authorization
context and checks performed. A fresh request nonce prevents reuse of an older
positive receipt for another verification request. Authorization requires
all evidence defined by the selected verification profile.

Credential issuer keys are configured through
`CREDENTIAL_TRUSTED_ISSUERS_JSON`. Native signing-key checks read the configured
Fabric key registry. Issuer trust, device enrollment, key status, credential
status and consent are separate requirements. Deployment must supply the real
identities and ledger connection before enabling this flow.

In the non-Fabric `test` profile, current key checks use the protected active
DCR registration and the explicitly active issuer-key configuration. Local
credential state is checked in the configured memory provider; it never counts
as an on-chain check. Verification requires the active credential record in
the configured provider. This profile supports cryptographic local testing
without a Fabric connection.

## ICA-backed first-controller activation without Fabric

In every non-demo network profile, first-controller activation verifies the ICA's
organization, legal-representative and service-controller credentials directly.
This ICA verification does not require a pre-existing device enrollment or a
Fabric connection. The configured network can separately require Fabric for
subsequent registry writes and enrolled-requester verification.
The receiving host is the presentation audience. Issuer signatures, credential
validity and the current ICA status must all pass before activation proceeds.

Each issuer in `CREDENTIAL_TRUSTED_ISSUERS_JSON` must have active pinned `jwks`
and a server-owned HTTPS `statusEndpointTemplate` ending in
`/network/credentials/{credentialType}/_status`. The client uses the ICA's
read-only asynchronous POST/POST protocol with a fresh thread. It sends the
complete signed credential type list, checks the returned identifier, type,
thread and timestamp, and rejects revoked, unknown or unavailable status.

The ICA-signed controller credential binds the business signing key to the
presenting actor. The outer registration transport key does not replace that
business key. Separately submitted credentials and controller signing keys must
match the signed presentation. Explicitly configured historical two-credential
onboarding still requires the shared controller policy and a signed actor-key
binding. Successful ICA-only verification reports `onChainChecked=false` and
`ledgerVerified=false`; it never claims a Fabric transaction. Native ICA
evidence is bound to the exact activation presentation and cannot be introduced
through the registration body or a remote operational verifier receipt.

## Gaia-X Digital Clearing House integration

The tenant-scoped gateway extension accepts an authenticated client's
tenant-signed presentation:

```http
POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/identity/gaia-x/standard-compliance
Content-Type: application/x-www-form-urlencoded
```

The gateway authenticates the registered client before selecting the tenant's
GXDCH provider from `GXDCH_TENANTS_JSON`. That configuration pins the provider's
HTTPS endpoint, issuer, verification keys and rules version. The gateway sends
the original `application/vp+jwt` presentation using the provider's VC-API
contract. It verifies the returned `application/vc+jwt` signature, validity,
`gx:LabelCredential`, SC label, configured rules version and exact coverage of
the submitted credential identifiers and canonical SHA-256 digests. The
original signed credential is returned unchanged. The credential issuer may
be a URI string or a W3C issuer object with `id`; this credential-profile
compatibility does not relax the issuer requirements for bearer JWTs.

The selected GXDCH engine performs Gaia-X schema and rule validation. The
gateway checks its signed result; it does not substitute a local success flag
for that validation. Professional access checks and Gaia-X conformity checks
have different inputs and outputs and can use different services.

## Explicit local demo

The local demo profile is selected explicitly with `SECURITY_MODE=demo` and
`NETWORK_MODE=test`. It provides demonstration transport, storage and
authentication behavior, while the wrapped KMS supplies real signing keys and
signatures. `CLEARING_HOUSE_MODE=stub` belongs to this profile.

Non-demo local `test`, deployed Test Network and production verify signatures
and current authorization state. `NODE_ENV=test` does not select demo behavior.
The runtime keeps the local demo profile separate from staging and production.

## Local participant-credential endpoint

This existing endpoint produces a signed description of the participating
organization from its stored legal-identity claims.

## Implemented endpoint

```http
POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/identity/oidc/credential
Authorization: Bearer <access-token>
Content-Type: application/json
```

The route:

- resolves an existing tenant and its DID document;
- builds a legal-participant credential from that tenant's stored claims;
- signs one `JsonWebSignature2020` proof with the host credential-signing key;
- uses `ML-DSA-44` by default, or the configured legacy signing algorithm when
  present;
- accepts `?pqc=true` or `X-PQC-Signature: true` to select `ML-DSA-44`.

In strict security mode, the bearer is verified by the configured application
authorization manager. The explicit local demo profile can enable its
demonstration bearer path.

## Published metadata

The tenant DID links to `/.well-known/openid-configuration` and
`/.well-known/smart-configuration` through the canonical OpenID and SMART
service entries. The SMART document advertises the tenant's verification
endpoint as `introspection_endpoint`, authenticated with `private_key_jwt`.
Clients discover the verifier there instead of requiring another expanded
operation list in the DID document. This endpoint checks SMART access; the
Gaia-X standard-compliance integration above has a separate purpose.

GW CORE publishes tenant-scoped OpenID and credential-issuer metadata through
the corresponding `/.well-known` routes. Those discovery documents describe
the local GW endpoints. The configured GXDCH engine publishes its own identity
and returns the signed conformity result.

## Boundary

This credential is a signed participant description. The GXDCH SC label above
is a separate credential issued by the selected conformity engine. It is not a login token, a SMART access
token, a Fabric enrollment certificate, or an ICA onboarding credential.

# Subject provider resolution and PDQm Patient matching

This is the human identity lookup contract for GW integrators. Public provider
discovery, private patient matching and data-access authorization are separate
operations.

## 1. Resolve only the index provider

The caller starts with a governed identifier: coding system, ISO jurisdiction
and value. GW normalizes `codingSystem|jurisdiction|value` and derives the
canonical SHA3-384 multihash asset id. The global `subjectidentifier-sc`
lookup returns only:

```json
{ "indexProviderDid": "did:web:index.example.org" }
```

The opaque asset id stops at Fabric. It is not a Patient identifier, public
card, authorization proof or provider query parameter. Fabric does not expose
the raw identifier, card, subject kind, contact data or clinical data.

The BFF resolves `indexProviderDid`, selects the advertised FHIR service, and
then sends the original authenticated identifier to that provider.

## 2. Match at the selected provider

Human matching uses IHE PDQm ITI-119 only:

```text
POST [base]/Patient/$match
```

The direct FHIR request body is one `Parameters` resource. Its repeated
`parameter[]` array contains exactly one input Patient under the `resource`
parameter:

```json
{
  "resourceType": "Parameters",
  "parameter": [
    {
      "name": "resource",
      "resource": {
        "resourceType": "Patient",
        "identifier": [
          { "system": "urn:oid:1.2.3.4.5", "value": "patient-123" }
        ]
      }
    },
    { "name": "onlyCertainMatches", "valueBoolean": true }
  ]
}
```

GW queries the provider's protected individual index using the governed
identifier and returns a native FHIR `Bundle` with `type: "searchset"`.
Internally stored schema.org `sameAs` is projected as a governed
`Patient.identifier`; `sameAs` is never emitted as a Patient property.

PIXm and `$ihe-pix` are not part of this contract.

## 3. Transport profiles

The clinical operation is identical in all profiles:

| Profile | HTTP content type | Request |
|---|---|---|
| Legacy FHIR | `application/fhir+json` | The single `Parameters` resource |
| DIDComm plain | `application/didcomm-plain+json` | One DIDComm message whose `body.data[]` has exactly one entry containing the Parameters resource |
| Strict | `application/x-www-form-urlencoded` | The same signed and encrypted DIDComm message in `request=<compact JWE>` |

The DIDComm entry has request metadata `{ "method": "POST", "url":
"Patient/$match" }`. Plain mode returns a DIDComm response envelope whose
`body` is the FHIR searchset. Strict mode returns
`response=<compact JWE>`; verification and decryption yield that same envelope.

The form fields are JAR/JARM-inspired framing around DIDComm. They are not a
claim that the compact object is a native OAuth JAR or JARM object. Channel and
smart-contract names are resolved inside GW managers and adapters; SDKs, BFFs
and portals never configure them.

## 4. High-level BFF call

Use the Node SDK method after DID resolution:

```ts
const matches = await runtimeClient.matchPatientAtIndexProvider({
  fhirBaseUrl,
  indexProviderDid,
  requesterDid: authenticatedActorDid,
  patient: {
    resourceType: 'Patient',
    identifier: [{ system: identifierSystem, value: identifierValue }],
  },
  onlyCertainMatches: true,
});
```

The SDK owns the Parameters resource, DIDComm envelope and selected transport.
The BFF supplies business inputs only. See the
[Node SDK 101](https://github.com/Global-DataCare/gdc-sdk-node-ts/blob/main/docs/101-PDQM_PATIENT_MATCH.md)
and the
[SDK Core contract](https://github.com/Global-DataCare/gdc-sdk-core-ts/blob/main/docs/101-SUBJECT_INDEX_PROVIDER_RESOLUTION.md).

# Professional consent and SMART identity

GW evaluates professional clinical access against one exact actor identity.
The canonical actor is the professional DID derived by
`buildProfessionalDidWeb(...)`; the employee/profile record, Consent
`actor-identifier`, professional VP credential subject and SMART request `sub`
must reuse that value.

An email-addressed Consent remains a compatibility rule for an email actor. It
does not automatically match the derived professional DID. Internal employee,
profile or resource UUIDs are also not actor DIDs.

The professional DID does not expose email plaintext. Its employee path uses a
SHA3-256 multihash of normalized email. A professional VC `sameAs` email uses
that exact multibase value with the ICA-compatible `urn:multibase:` prefix.

An earlier SHA3-384-derived professional DID remains a different actor.
Profiles, Consent grants and VP material must be migrated or reissued
consistently; GW does not silently equate the old and new DIDs.

Clinical permissions use shared `HealthcareConsentActions`. A SMART request
must request only capabilities covered by the active Consent. In particular,
`organization/Consent.cruds` requires its own resource permission and must not
be appended to an otherwise section-only clinical read.

The OAuth client/device `client_id` remains distinct from the professional
actor DID. A `client_assertion` authenticates that client and its `aud` must be
the concrete SMART token endpoint.

High-level callers should omit `audience`. A trusted SDK runtime may start
discovery from an index service, but the final audience and transport target
are the resolved provider DID service entry
`#identity:openid:smart:token`. The index base URL itself is not the token
audience. Without a discovery adapter, the SDK uses the exact SMART endpoint
for its configured GW and tenant route.

This access decision is independent of the ledger adapter. The same vault
Consent evaluation applies in `NETWORK_MODE=test`; Fabric is not required
merely to issue the SMART token.

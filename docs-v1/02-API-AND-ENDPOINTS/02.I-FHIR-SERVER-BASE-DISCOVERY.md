# FHIR server-base discovery

## Canonical base identity

The tenant and sector identify the hosted data plane:

```text
/{tenantId}/cds-{jurisdiction}/{version}/{sector}
```

A FHIR server base adds the subject section and the native FHIR wire format:

```text
/{tenantId}/cds-{jurisdiction}/{version}/{sector}/{section}/{format}
```

Examples of independent server bases are:

```text
/{tenant}/cds-{jurisdiction}/v1/{sector}/individual/org.hl7.fhir.r4
/{tenant}/cds-{jurisdiction}/v1/{sector}/digitaltwin/org.hl7.fhir.r4
```

`individual` is the operational subject record. `digitaltwin` is the
pseudonymous research projection. They are separate authorization,
persistence and capability surfaces; the projection is not a second copy of
the operational EHR.

## Standard discovery endpoints

Discovery is relative to each exact server base:

```text
GET [base]/metadata
GET [base]/.well-known/smart-configuration
```

`[base]/metadata` returns a FHIR `CapabilityStatement` with `kind=instance`.
Its `implementation.url`, `fhirVersion`, resource types and supported endpoint
actions are derived from the matching tenant DID service selectors. A tenant
must not advertise resources belonging to another section, another FHIR
release or a capability it has not activated.

The path layout is the same for R4 and R5, while the returned
`CapabilityStatement` must use the corresponding FHIR release. R4 advertises
`fhirVersion=4.0.1`; R5 advertises `fhirVersion=5.0.0`.

## Native FHIR versus the flat-claims contract

`org.hl7.fhir.r4` and `org.hl7.fhir.r5` are native FHIR wire formats and may
expose the standard discovery endpoints above. `org.hl7.fhir.api` is the
claims-first API context used by GW and SDK contracts; it is not a native FHIR
release and must not expose a misleading FHIR `CapabilityStatement`.

The flat-claims layers remain distinct:

1. Canonical claim names are the FHIR SearchParameter names published in the
   resource's `#search` catalog.
2. Standard FHIR extensions retain their canonical extension URL and may use a
   resource-qualified flat form such as `ResourceType.extension-name`.
3. Any non-standard extension is described simply as a custom extension. It
   must have an explicit canonical URL and must not be labelled as GDC-owned.
4. Native FHIR resources and documents are materialized only at an explicit
   import, projection or export boundary. The protected canonical store remains
   claims-first.

For IPS-supported resource types, create and card-display adapters support the
fields, cardinalities and value sets required by the applicable IPS profile.
The tenant capability statement still advertises only the resources and
operations implemented for its exact server base.

## Payload boundaries

The base identifies the server; it does not make every stored object a native
FHIR resource. Application exchanges commonly carry FHIR Bundles, including
Communication payloads and attachments, Consent documents and IPS documents.
Research updates may also arrive as an IPS document Bundle or through an
explicit conversion/import adapter. Authorization remains outside the FHIR
payload and is enforced independently for `individual` and `digitaltwin`.

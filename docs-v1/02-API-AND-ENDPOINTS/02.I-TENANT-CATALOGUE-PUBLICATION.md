# Publish products and services to your tenant catalogue

Call the publishing function in the Global Data Care portal backend after the
organization controller approves the listing. The controller must already
have a registered profile for the destination tenant.

## Publication and withdrawal lifecycle

The portal backend sends approved public listings to the organization tenant
on the gateway configured for its controller profile. All paths below are
relative to that gateway origin.

| Step | Endpoint | Result |
| --- | --- | --- |
| Add an individual listing | `POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/organization/org.schema/Catalog/_upsert` | Publishes each new `type` and `id` in the submitted batch. |
| Update an individual listing | Same `_upsert` endpoint | Replaces the complete listing with that `type` and `id`. Unmentioned listings stay published. Send every field you want to keep. |
| Replace the imported catalogue | `POST /{tenantId}/cds-{jurisdiction}/v1/{sector}/organization/org.schema/Catalog/_publish` | Replaces the previous imported snapshot with the complete submitted list. Listings published individually remain visible, and their versions take precedence when the same `type` and `id` also appear in the snapshot. |
| Confirm and read back | `POST …/Catalog/_upsert-response` or `POST …/Catalog/_publish-response`, then `GET …/dsp/catalog/offerings.json` | Check the receipt for the same operation and compare the public listing fields. |
| Withdraw a snapshot listing | Send a new `_publish` snapshot without that listing | The omitted listing disappears if no individual version is published. The snapshot must contain at least one listing. |
| Withdraw an individual listing or clear the entire catalogue | Pending | Gateway Core still needs an explicit withdrawal operation. Omission from an `_upsert` batch leaves the listing published. |

For example, if A and B are published individually, submitting a modified B
and a new C through `_upsert` leaves A, the updated B and C visible. The
receipt count is two because it covers the submitted operation.

## Install the portal dependencies

```bash
npm install --save-exact gdc-sdk-node-ts@2.9.33 gdc-common-utils-ts@2.9.33
```

Reuse the BFF's configured `ServerProfileSessionManager`. Its constructor takes
the existing profile store, profile sealer, gateway origin, recipient-DID key
resolver and app identity. Follow the
[registered controller example](https://github.com/Global-DataCare/gdc-sdk-node-ts/blob/main/docs/101-SDK_END_TO_END.md)
to set up that manager.

## Reopen the controller and publish or update a listing

```ts
import type { ServerProfileSessionManager } from 'gdc-sdk-node-ts'
import { buildCataloguePrimaryDocument } from 'gdc-common-utils-ts/convert/ocean-catalogue'

type ControllerSession = Parameters<ServerProfileSessionManager['openOrganizationController']>[0]
type CatalogueEntry = Parameters<typeof buildCataloguePrimaryDocument>[0][number]
type Offering = CatalogueEntry & { type: 'Product' | 'Service' }
type CatalogueAction = '_upsert' | '_publish'

export async function publishTenantOfferings(
  profileSessions: ServerProfileSessionManager,
  controllerSession: ControllerSession,
  reviewedEntries: readonly Offering[],
  operationId: string,
  action: CatalogueAction = '_upsert',
) {
  if (!reviewedEntries.length) throw new Error('The catalogue submission is empty.')
  const document = action === '_upsert'
    ? buildCataloguePrimaryDocument(reviewedEntries)
    : { jsonapi: { version: '1.1' }, data: reviewedEntries }
  const { profile, sdk } = await profileSessions.openOrganizationController(controllerSession)
  const { tenantId, jurisdiction, sector } = profile.routeContext
  const route = [tenantId, `cds-${jurisdiction}`, 'v1', sector].map(encodeURIComponent).join('/')
  const path = `/${route}/organization/org.schema/Catalog/${action}`

  const { poll } = await sdk.submitAndPoll(path, `${path}-response`, {
    thid: operationId,
    iss: profile.actorDid,
    aud: profile.providerDid,
    client_id: profile.clientId,
    type: 'application/didcomm-plain+json',
    body: document,
  })

  const receipt = poll.body as { type?: string; thid?: string; body?: { total?: number } }
  if (receipt?.type !== 'org.schema.catalog-publication' ||
      receipt.thid !== operationId || receipt.body?.total !== document.data.length) {
    throw new Error('The gateway did not confirm the complete catalogue update.')
  }
  return { published: receipt.body.total }
}
```

- `controllerSession.ownerId` and `idToken` come from the authenticated BFF
  session. `profileId` identifies the registered controller selected by that
  account. Pass either `pin` through the existing unlock flow or
  `authorizedWalletSeed` from the BFF's protected custody.
- The SDK restores the registered keys and signs and encrypts the request.
  The sender DID, recipient DID, client ID and tenant route come from the
  profile that the SDK opened.
- `reviewedEntries` contains the approved public product or service resources.
  Each has a stable ID and Schema.org attributes such as `name`, `description`,
  `category` and `offers`. Use `offers: []` for a listing without a commercial
  offer. For `_upsert`, send products and services in separate batches. For
  `_publish`, send the complete snapshot in one request. The gateway sets the
  publisher from the tenant.
- `operationId` is the identifier the BFF stored for this approved change.
  On retry, reuse it and the same listing IDs.

## Add two services and a product

Save the previous example as `publish-tenant-offerings.ts` in the BFF.
Use a development tenant and three operation IDs saved with the three approved
changes. Replace the sample IDs and public fields with the listing data from
your portal. Each call uses `_upsert`.

```ts
import { publishTenantOfferings } from './publish-tenant-offerings.js'

type PublishArguments = Parameters<typeof publishTenantOfferings>

export async function addDevelopmentListings(
  profileSessions: PublishArguments[0],
  controllerSession: PublishArguments[1],
  operations: { firstService: string; secondService: string; product: string },
) {
  await publishTenantOfferings(profileSessions, controllerSession, [{
    type: 'Service',
    id: 'data-hosting',
    attributes: { name: 'Data hosting', description: 'Host a data catalogue', category: 'Hosting', offers: [] },
  }], operations.firstService)

  await publishTenantOfferings(profileSessions, controllerSession, [{
    type: 'Service',
    id: 'data-integration',
    attributes: { name: 'Data integration', description: 'Connect a data source', category: 'Integration', offers: [] },
  }], operations.secondService)

  await publishTenantOfferings(profileSessions, controllerSession, [{
    type: 'Product',
    id: 'sensor-kit',
    attributes: { name: 'Sensor kit', description: 'A device kit for data collection', category: 'Devices', offers: [] },
  }], operations.product)
}
```

After the second call, both services remain visible. After the third call,
the catalogue contains both services and the product. The two services could
also be sent together in a single `Service` batch. The product uses a separate
`Product` batch. To edit the second service, submit its full updated fields
with the same `Service` type and `data-integration` ID and a new operation ID.

## Verify the result

1. Open the tenant's public `/dsp/catalog/dcat.json` under its tenant base URL.
2. Follow the offering catalogue link in `dcat:service` to
   `/dsp/catalog/offerings.json`. Find the listing by its `type` and `id`,
   and compare the updated fields before reporting success in the portal.
3. Confirm the host catalogue lists that tenant catalogue in `dcat:catalog`.

### Check the lifecycle in a development tenant

1. Run the two-service and one-product example. Update the second service
   using the same ID and full approved fields. Check that the first service
   and the product are still visible with their original values.
2. Import a snapshot with two different listing IDs. Replace that snapshot
   with one that omits one of its listings. Confirm the omitted item disappears
   and the individually published listings remain visible.
3. Record individual withdrawal and clearing the catalogue as pending. Those
   steps require a gateway operation and public readback before the portal can
   offer a withdrawal action.

A commercial listing update changes the public listing feed referenced from
DCAT. A signed Gaia-X service offering has its own issuance and terms.
An external dataset and its access services require their own publication
contract for `Dataset` and `DataService`.

## Prepare datasets already published in Pontus-X

Run the conversion in the portal backend with the resolved Ocean DDOs for
the organization. The optional `landingPage` is the public asset page the
portal already knows.

```ts
import {
  buildCataloguePrimaryDocument,
  projectOceanDatasetEntries,
} from 'gdc-common-utils-ts/convert/ocean-catalogue'

export function preparePontusDatasets(
  sources: readonly { ddo: unknown; landingPage?: string }[],
) {
  return buildCataloguePrimaryDocument(sources.flatMap(projectOceanDatasetEntries))
}
```

The resulting JSON:API document preserves the external DID and includes each
`Dataset` and its linked `DataService` entries. Publication of those resources
requires the external dataset contract and a verified readback from the target
tenant. The `Catalog/_upsert` example above implements the product and service
contract.

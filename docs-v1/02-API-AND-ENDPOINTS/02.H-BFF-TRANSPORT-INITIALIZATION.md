# BFF and EHR transport initialization

The FHIR resource, the authenticated actor and the wire carrier are separate
layers. Changing `application/fhir+json`, DIDComm plain or encrypted DIDComm
must never change the clinical author, attester, SMART subject or permission.

## Decision table

| Client state | Request carrier | Required proof | Failure rule |
| --- | --- | --- | --- |
| Initial device-enrollment bootstrap | Authenticated DIDComm plain on a narrowly scoped compatibility endpoint | Verified HTTP bearer whose stable contact matches every requested owner contact | Produce only the activation/enrollment grant; reject mismatch and never invent a DCR client |
| Enrolled first-party BFF profile | Form `request=<JWE(DIDComm)>` | Registered DCR signing/encryption keys plus the applicable bearer/SMART token | Fail closed if the wallet/profile cannot be opened |
| External EHR | Native `application/fhir+json` on an explicitly enabled compatibility deployment | OAuth/SMART bearer and integration policy; mTLS/FAPI when required | Reject untrusted issuer/audience/scope |
| Local demo | Explicit demo plaintext | Test-only credentials | Never run with production `NODE_ENV` |

`DIDComm plain` still travels over HTTPS/TLS; it lacks only DIDComm
message-layer encryption. Native FHIR contains no DIDComm `from`, `iss` or
`kid`. HTTP authorization remains outside the FHIR Bundle.

## First-party BFF composition

A portal installation and a telephone installation are separate DCR devices.
Each receives its own `client_id`, `kid` and independently generated wallet
seed protected by that device's custody envelope. Authorizing both for the same
controller does not split or copy one seed between them.

```ts
const active = Boolean(profile.dcrClientId);
const gateway = createGatewayRuntime({
  transportProfile: active
    ? TransportProfiles.DidcommEncryptedForm
    : BootstrapTransportProfiles.AuthenticatedDidcommPlain,
  secureTransportAdapter: active
    ? await profileRuntime.openSecureTransport(profile)
    : undefined,
});
```

These illustrative names express the boundary; use the concrete SDK runtime
owned by the consuming BFF. The composition root selects the profile from
trusted configuration/lifecycle state. Browsers, payloads and individual route
handlers cannot request a downgrade. Submission and polling use the same
selected profile.

## GW environment examples

Protected post-DCR first-party deployment:

```env
SECURITY_MODE=strict
FHIR_LEGACY=false
JSON_LEGACY=false
DIDCOMM_PLAIN=disabled
DEMO_ALLOW_INSECURE_BEARER=false
```

Authenticated interoperability/bootstrap deployment:

```env
SECURITY_MODE=compat
FHIR_LEGACY=true
JSON_LEGACY=false
DIDCOMM_PLAIN=true
DEMO_ALLOW_INSECURE_BEARER=false
```

This second profile affects the complete GW instance. Do not use it as a
production substitute for a route-scoped bootstrap or interoperability
endpoint. After enrollment, a first-party device uses its registered wallet;
failure to open it never selects the compatibility carrier.

FHIR compatibility is a representation requirement, not authorization.
